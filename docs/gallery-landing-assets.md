## C. 設計決策記錄

### 1. 捲動動效用 rAF + CSS var，不引 GSAP／Lenis

需求全是「捲動位置 → 0~1 進度 → transform」的純函數：pin 用 `position: sticky`（零 JS），視差與 scroll-grow 各是一個進度值。GSAP 的 timeline scrub 用不上，卻要多背一套動畫心智模型；Lenis 劫持原生捲動，會連帶影響 sticky、鍵盤翻頁與 reduced-motion 的處理路徑。

改為照搬 `InviteStage` 既有慣例：事件只設旗標 → rAF 節流 → **JS 只寫 CSS var、不碰 `style.transform`**。CSS var 也保留升級路徑：日後若真要敘事級捲動，只換「寫 var 的那一側」，CSS 消費端一行不動。

`useScrollProgress` 是**全域單例**：整站一個 rAF loop、一個 IntersectionObserver（`rootMargin: 20%` 控制活性名單），landing 三個區塊與系列頁數十張照片共用，不會各自起 loop。幾何在 resize 時重量測並快取，捲動中不讀 `getBoundingClientRect`。

原本計畫寫的「視差 var 加 lerp 阻尼」實作時拿掉了：視差是 scroll-linked 而非慣性動畫，加 lerp 反而讓畫面落後於手指。直接映射就是對的。

### 2. CSS var 的預設值一律取「構圖中性位」

- `--sp: 0.5`（區塊捲動進度）→ 視差欄停在中段
- `--gp: 1`（距視窗中心）→ 照片全尺寸
- `--load-p: 1`（描線進度）→ 字樣完整
- `data-active="true"`（名字是否就位）→ SSR 預設可見

因此**沒有 JS、或使用者開了「減少動態」時，畫面是完整的靜態版本**，沒有任何元素被 `opacity: 0` 藏死。開場疊層則整個包在 `<ClientOnly>` 內、且 reduced-motion 時直接不渲染。

### 3. Union.svg 的描線：把輪廓本身當筆刷，沿筆順「寫」出來

素材是**輪廓化字形的單一 fill path**，沒有 stroke。演進過兩版：

**第一版（已汰換）**：`mask-image: linear-gradient()` 由左往右直線 wipe。合規、穩定，但那是「一道直邊掃過去」，不是書寫。

**現行版**（`GalleryLogoMark.vue`）：採用手寫動畫的正統做法——**把同一條路徑當成筆刷放進 `<mask>`，用很粗的描邊沿路徑行進方向掃過去**，揭開底下的填色字樣。填色只存在於字的範圍內，所以筆刷溢出邊界不影響結果。三個關鍵：

1. **不能直接對 fill path 下 `stroke-dashoffset`**：那畫的是字的「外框輪廓」，筆劃兩側各走一條線，視覺是雕邊不是書寫。輪廓只能當「筆刷的軌跡」用，不能當可見的線。
2. **方向要反著走**（`stroke-dashoffset` 取負，從路徑末端往回揭）：這條輪廓的起點在字的中段，正著走會從右側先冒出來。實測比對過正向／反向兩種取樣序列，反向才是由左至右照筆順寫出來。
3. **筆刷粗細 30（viewBox 單位）**：24 以下字心會留沒填滿的縫，46 以上會一次揭開旁邊的筆畫（實測 24／34／46 三檔比較）。

另外輪廓末端有一小段落在字的外側，進度前 14% 畫面上看不出變化，故把 0~1 重新映射到 0.14~1，開場不會有一段乾等。

> **`pathLength` 在 Vue 模板裡會失效**（踩過）：SVG 屬性大小寫敏感，`pathLength` 經模板編譯會變成 `pathlength` 而不被認得。當時的症狀很有迷惑性——不是動畫壞掉，而是 `stroke-dasharray="1 1"` 落在長度 3102 的實際路徑上變成 1 單位的密集短點，圓端點又把它們接成實線，看起來就像「一開始就寫完了」。改成 `onMounted` 時用 `getTotalLength()` 量真實長度、以使用者單位下 dasharray。

### 4. 進度是真的，不是假動畫

預載 6 張（蒙太奇 5 張 + hero），`new Image()` 計數，**onerror 也計數**——少一張圖不該讓開場卡在 80%。顯示值取「實際載入比例」與「最短時長 900ms」的較小者：既等圖，快取命中時也不會 0 直接跳 100。另有 5 秒硬上限強制放行。

計數器是直式滾輪，只動 `translateY`。Cormorant 是舊體數字（3、4、9 有下伸部），格高必須留 1.4em 才不會被裁掉；滾動 150ms——進度更新很密，時間長了整段都在滑動中、讀不出數字。

**計數的內容不是百分比，是「在一起的天數」**：從 `togetherSince`（2015-05-21）數到今天，載入進度把它從 0 推到今天的天數（2026-09-01 是 4121 天），右側的單位字是 `Days`。天數是每次開場即時算的，不寫死。欄數取總天數的位數（目前 4 欄），前導的 0 留著位置但 `opacity: 0`，所以開場不會出現「0000」、數字也不會左右跳。

### 5. hero 的交接靠「幾何重合」，不靠量測

疊層最後那張 hero 卡片的**版面盒直接就是最終 hero 的位置**（`position: absolute; inset: var(--gallery-frame)`），開場期間只用 `transform: scale(0.26)` 把它縮回中央當成一疊照片的最後一張，放大即 `scale(1)`。底下 SSR 的 `GalleryHero` 是同一張圖、同一個框（`.gh-root` 的 padding = 同一個 `--gallery-frame`），放大結束時兩者像素級重合，疊層淡出就是無縫定格——不需要任何 FLIP 量測或 JS 幾何計算。

`--gallery-frame` 宣告在頁面根元素上，靠 CSS 自訂屬性的繼承傳給兩個子元件，兩邊不會各寫一份 clamp 而走鐘。

開場期間會 `scrollTo(0, 0)` 並鎖 `body` 捲動：疊層的卡片以視窗為準定位，頁面沒停在最上面就對不齊（例如重整時瀏覽器還原了捲動位置）。

### 6. 動效超出 creative-direction §4「一頁最多一個主動效」——刻意延伸

相簿頁同時有：開場（描線 + 蒙太奇 + hero 放大）、系列區塊的釘住視差與逐字進出、系列內頁的捲動放大。比照 `invite-portal-assets.md` §C-2 的判定，視為**單一敘事語彙**（「翻開一本相簿」）：開場是掀頁、捲動視差與放大是同一語彙的延續。

§4 的三條硬原則未破：

- **reduced-motion**：`GalleryPreloader` 命中即 `emit('done')` 且整個疊層不渲染（實測疊層數 0）；`useScrollProgress` 命中即不啟動，所有 var 維持中性預設。CSS 全域 guard 另行兜底。
- **只動 transform / opacity**：無 layout 屬性 transition、無 `transition-all`。系列內頁的「放大變寬」是 `scale(0.86→1)` 而不是改 `width`，避免逐幀重排。
- **duration 與 ease**：互動 transition 走 150／250／400ms + `--ease-standard`／`--ease-emphasized`；開場的 420ms／900ms／1900ms 是編排級 keyframes，寫在 `<style scoped>`（同 invite 頁 950ms 的先例）。

### 7. 「首屏文字 1 秒內就位」讓位給 cinematic 開場

開場約 3.5 秒（載入 ≥0.9s + 蒙太奇與放大 2.6s），這是使用者明確要求的體驗。配套：

- 右下角常駐「跳過開場」按鈕，Esc 或點按鈕立即結束
- 5 秒逾時硬上限，圖片載不完也會放行
- reduced-motion 與無 JS 直接看到完整靜態頁（見 §2）
- 依使用者決定**每次整頁載入都播**（未做 sessionStorage 記憶）；SPA 內部導航（例如從系列頁按返回）不會重播，因為元件不重新掛載

### 8. 系列名的「交叉淡換」是等效方案，不是逐幀復刻

參考站用單一全域 pin 節點在區塊交界處抽換內容，做出無縫交叉。本頁改為**每個區塊各自 sticky**，靠相鄰兩個 sticky 的自然交接產生「上一組退、下一組進」——狀態複雜度低很多，視覺結果接近。逐字進出由 `--sp` 落在 [0.08, 0.92] 區間切換 `data-active`，delay 用 `calc(var(--i) * 40ms)`。

### 9. hero 的標語拆成四邊大字

標語不放在畫面中央，而是拆成四個字圍在照片四邊：上 `Shine`（與 `Happy` 每 3.4 秒輪換）、左 `in`、右 `your`、下 `Love`。往下捲時四個字各自朝外散開並淡出，照片同時微微推近（`scale(1 + hp*0.06)`）。首屏只有這四個字、署名與倒數，沒有副標與 CTA——四個字本身就是標語，再加一句中文副標會變成同一件事講兩次。

**上方的字會壓到人臉**（實測過）：四個字的位置是固定的，照片的裁切卻隨視窗比例變。視窗越扁，`object-fit: cover` 垂直裁掉越多，人物在畫面裡越往上跑——1600×700 時人臉正好落在上方大字的位置。解法是 `object-position: center 22%`：裁切時多留上緣、少留下緣，把人物壓到畫面偏下（視窗越扁效果越明顯，剛好對症）。另外上方那個字比其他三邊小一號（`clamp(2rem, 6vw, 5.25rem)`）、上緣漸層加重到 44%。

- 捲動進度 `--hp` 用 `useScrollProgress` 的 **leave 模式**：滿版 hero 的高度等於視窗高，block 模式沒有可捲行程（`height - viewport = 0`）算不出進度，所以另加一個「已捲掉幾個視窗高」的模式。預設 0＝全部就位。
- **語意**：畫面上的四個字是視覺呈現，`aria-hidden`；完整標語放在 `<h1 class="sr-only">`，螢幕閱讀器與 SEO 讀到的是一句完整的話，不是四個散字。
- 文字輪換是 JS 驅動的（`setInterval`），繞得過 `main.css` 的 CSS guard，故自行 `matchMedia` 判斷 reduced-motion——命中就停在第一個字。

字級用 `clamp(2.25rem, 7vw, 6rem)` 寫在 `<style scoped>`（本檔不在公開頁白名單）。

### 10. 婚禮倒數：橫排再旋轉成直式

`GalleryCountdown.vue` 貼在 hero 右緣，DAY／HR／MIN／SEC 由上往下讀，倒數歸零後整條換成 `We're married!`。

- **排版**是一列橫的再整條 `rotate(90deg)` 立起來。置中不能靠 grid／flex：橫列（約 300px）比右緣窄框（約 50px）寬得多，**溢出時對齊會退回 start，整條會被推出畫面外**（實測 x 落在 1477、視窗只有 1440）。改用絕對定位的置中慣用法 `left/top: 50% + translate(-50%, -50%) rotate(90deg)`——translate 的百分比取元素自身寬高，在旋轉之後作用於外層座標，剛好把旋轉後的中心對回窄框中心。
- **時間只在 mounted 之後才算**：SSR 與首次渲染都不輸出數字，避免 hydration 兩端對不上。
- **無障礙**：每秒跳動的數字若進了無障礙樹會被反覆讀出，故視覺列 `aria-hidden`，另給一句靜態的「距離婚禮還有 N 天」。
- 目標時間 `weddingAt: '2026-11-22T12:00:00+08:00'`（入席時間，見 `useStoryContent` 的 `venue.dateTime`）。

### 11. 版面上的兩個實測修正

- **手機的系列區塊**若沿用桌機「左中文、右英文」的橫向排法，英文會被右側照片整個蓋掉：手機改成中英文疊成一欄靠左、照片讓到右半邊，1024px 以上才橫向展開。

### 12. hero 輪換大字加掃光（Vue Bits ShinyText 移植）

新人指定「Shine／Happy 這兩個字要有掃光效果」。`app/components/ShinyText.vue` 是 Vue Bits ShinyText 的移植，用 `background-clip: text` + 動畫 `background-position`，讓一道比底色亮的高光橫掃過文字。

**接法**：掛在 `.gh-word-top` 的 `<Transition>` 裡。換字時整個元件重掛，掃光因此每次都從頭跑一次——字出現 → 掃一道光 → 停 → 換下一個字，剛好跟 3.4s 的輪換節奏對上（`speed: 1.6` + `delay: 1.1`）。

**底色 86% 是量出來的折衷**。掃光的可見度＝底色與高光的差距，但底色壓太低，這個字在靜止時就會比 `in`／`your`／`Love` 那三個實心紙白的兄弟暗一階，看起來像壞掉。實測：68% 明顯偏灰，86% 掃光仍看得出來、靜止時也對得上。純白掃純白（100%）則完全看不見。

**與 `creative-direction.md` §3「禁 gradient text」同一個機制，屬刻意例外。** 該條禁的是彩色漸層字那種 AI 模板味；這裡是同色系的高光掃過（紙白 → 純白 → 紙白）。lint 只擋 Tailwind 的 `bg-clip-text` class，本元件走 inline style 不會被攔，所以這個例外靠這段紀錄，不靠工具。

**移植時改了五處**（見元件抬頭註解）：拿掉 `className` prop 改用 attribute fallthrough、`prefers-reduced-motion` 時整個不套漸層而非只停動畫、顏色吃 CSS var、方法改 `function` 宣告，以及下面這一項。

**兩個把人卡住的移植坑：**

- **`<Motion tag="span">` 在 motion-v 2.x 是 `as` 不是 `tag`。** Vue Bits 給的原始碼是對著舊版寫的。
- **template 裡的註解在 dev 模式下也算節點**，會讓元件變成多根。外層的 `<Transition>` 只收單一根，於是整個渲染不出來——**而且不報任何警告**，DOM 只留下 `<!--[--><!--]-->` 一個空 fragment。查了兩輪才發現。同理，元件若寫成 `v-if`／`v-else` 兩個根，外部傳進來的 `class` 也會無處 fallthrough；本元件因此只留單一根，關閉時改用「不給 style」表達。

### 13. 全站賓客頁的點擊回饋（Vue Bits ClickSpark 移植 + 自加小愛心）

新人要求「網站裡面的 click 互動」要有火花，並且「冒出 icon 小愛心往上飛出消失」。`app/components/ClickSpark.vue`：一張 canvas 覆蓋層，每次點擊在指標處炸開 8 道金色短線，同時飄起一顆金色小愛心（往上 46px、左右輕晃、900ms 淡出）。

**掛載範圍是賓客面向的兩個 layout**：`story.vue`（`/invite`、`/gallery`、`/story`）與 `guest.vue`（RSVP／報到／祝福／謝卡）。**後台的 `default.vue`／`auth.vue` 不掛**——`creative-direction.md` §4「後台幾乎不動」，而且婚禮當天接待台正在用它工作。

**移植時的五處改動**（見元件抬頭註解），其中兩項是必要的而非美化：

- **不再用 `<div class="relative w-full h-full">` 包住內容。** 原版是包裹式元件，那個 `h-full` 套到既有版面上會塌掉，而且得逐頁包一層。改成 `position: fixed` 的覆蓋層 + 監聽 `window`，對版面零影響。canvas 的 CSS 尺寸就是視窗，所以繪圖座標直接用 `clientX/Y`，不必再換算。
- **rAF 只在畫面上還有東西時跑。** 原版掛著一個永不停止的 `requestAnimationFrame` 迴圈；那是 demo 頁的寫法，常駐在公開頁會一直吵醒合成器、吃行動裝置的電。改成點擊時啟動、火花與愛心都演完就把迴圈收掉。

其餘三項：依 `devicePixelRatio` 放大 backing store（retina 上線條才不糊）、顏色從 `--color-gold`／`--color-gold-deep` 讀而非寫死色碼、`prefers-reduced-motion` 時完全不註冊監聽（canvas 走 JS 動畫，繞得過 `main.css` 的 CSS guard）。

canvas 是 `pointer-events: none` + `aria-hidden`，`z-index: 9999` 讓火花能出現在任何東西之上（含 modal 與 toast），但不擋任何點擊。

### 14. 系列頁照片流：每張的行程不一樣

原本每張照片的進場一模一樣（統一 `scale(0.94 → 1)`），滑起來像同一個動作重播十次。改成**每個版位各有自己的行程**：

| 版位 | 比頁面慢多少（桌機） | 橫向偏移 | 最遠縮到 |
|---|---|---|---|
| 置中中圖 | 4vh | — | 0.96 |
| 左大 | 7vh | -1.1vw | 0.93 |
| 右小 | 12vh | 1.6vw | 0.90 |
| 滿版出血 | 照片在框內走 9% | — | — |
| 左小 | 11vh | -1.6vw | 0.90 |
| 右大 | 5vh | 1.1vw | 0.94 |
| 置中小圖 | 9vh | — | 0.92 |

規則是**小圖拖得慢、大圖幾乎跟著頁面走**——遠的東西移得慢，這是視差的物理依據，不是隨機給值。數字刻意不成等差：等差看起來還是「一起動」，差距要參差才像各走各的。

兩件實作上的事：

- **滿版那張不能整塊位移**，一移邊就露出來。改成框釘死、照片在框內自己上下走（`scale(1.12)` 換來上下各 6% 的餘裕，位移最多走 4.5%）。
- **`--gp` 改成帶方向的 `--gt`。** 位移要知道往哪邊推，只有「離中心多近」是不夠的。`useScrollProgress` 因此把 `center` 模式換成 `travel`（0＝還在視窗下方、0.5＝正對中心、1＝已捲到上方）。壓暗與暖光仍然只要「多近」，在 CSS 端用 `max()` 折回來即可，不必為此多註冊一個變數——`abs()` 的瀏覽器支援還不夠，`max(x, -x)` 是等效寫法。

`--gt` 預設 0.5＝正對中心＝定位尺寸，所以 reduced-motion 或無 JS 時所有照片都停在 `scale(1)`、零位移、零壓暗，就是一般的靜態排版。

### 15. 開場最後一張的放大中間頓一下

原本是 900ms 一路衝到底。改成 1400ms 並在 keyframe 內逐段指定 timing function，速度曲線分成四段：

| 時間 | scale | 感覺 |
|---|---|---|
| 0 → 8% | 0.26 | 淡入，還沒動 |
| 8 → 50% | 0.26 → 0.80 | 一口氣長到接近滿版（峰值 2.2/s） |
| 50 → 62% | 0.80 → 0.83 | **頓一下**（0.12~0.18/s，幾乎停住） |
| 62 → 100% | 0.83 → 1 | 再推一次，最後慢慢貼上（收尾 0.05/s） |

`animation-timing-function` 寫在 keyframe 裡才有分段控制；只給 shorthand 一個 easing 是做不出頓點的。

連帶調整：`SHOW_MS` 2600 → 3100（1500ms 起跑 + 1400ms 放大 + 收尾餘裕），蒙太奇的推近 1900ms → 2400ms——不然放大那段的背後會定格不動。

### 16. 相簿首頁的系列區塊：照片流（對照 adovasio.it 重做）

原本的做法是把七張照片絕對定位排成三列，釘在一個 100vh 的 sticky 區塊裡，每張給一個很大的視差幅度（-38vh ~ -190vh）。捲起來有兩個毛病：**照片會擠在一起**、**大小落差不夠**。

截了參考站 https://www.adovasio.it/ 量它的 DOM，兩個毛病都有結構性的成因：

| | adovasio.it | 改之前 | 改之後 |
|---|---|---|---|
| 照片寬度範圍 | 17vw → 52vw（3.1 倍） | 15vw → 22vw（**1.5 倍**） | 14vw → 44vw（3.14 倍） |
| 每張照片佔多少捲動 | 0.84 個視窗 | 0.43 個視窗 | 0.66 個視窗 |
| 照片相對頁面的速度 | 0.85× ~ 1.0×（差 15%） | **0.19× ~ 0.95×（差 5 倍）** | 0.83× ~ 0.93× |
| 排列方式 | 一條垂直照片流 | 絕對定位排成三列 | 一條垂直照片流 |

**「擠在一起」的根因是速度差，不是間距。** 每張照片有自己的視差幅度時，慢的幾乎黏在畫面上、快的用接近頁面的速度衝上來，**快的一定會追上慢的**。間距變成「速度差算出來的結果」，不是能直接控制的量。參考站的速度差只有 15%，所以永遠不會撞。

**「沒層次」的根因是排成列。** 一排三張要塞進畫面寬的 2/3（66vw），每張最多 20vw，大小範圍被結構鎖死在 1.5 倍。參考站從不把三張排成一線，所以最大能做到 52vw。

#### 結構：被釘住的是名字，不是照片

```
<section class="ss">              高度由內容決定；overflow-x: clip
  <a class="ss-link">             拖曳手勢 + 導向系列頁
    <div class="ss-stage">        sticky top:0 / 100dvh / z-index 1 —— 系列名
    <div class="ss-foot">         sticky top:0 / 100dvh / z-index 3 / margin-top:-100dvh —— 系列說明
    <div class="ss-stream">       z-index 2 / margin-top:-100dvh —— 照片，正常文件流
```

照片走**正常文件流**，間距是真的 `margin-top`，所以撞不到。名字在照片之下（照片壓過大字，與參考站一致），系列說明在照片之上（它是要讀的字，不能被照片切掉）。

三個實作上的坑：

- **`overflow-x` 必須用 `clip` 不能用 `hidden`**——`hidden` 會讓子層的 `position: sticky` 整個失效。
- `.ss-foot` 與 `.ss-stream` 各自 `margin-top: -100dvh` 疊回 stage 上，區塊總高才等於照片流的高度。
- `.ss-stream` 內不能有 transform，否則會變成 sticky 的 containing block，把名字釘死。

#### 視差：`travel` 模式 + 8~20vh

每張照片用 `useScrollProgress` 既有的 `travel` 模式寫入 `--gt`（`GallerySeriesFlow`、`GalleryInterlude` 同一套）。`--gt` 在 1.2 個視窗的行程內走完 0→1，所以 `--lift` 為 L 時相對頁面的速度是 `1 - L/120`：8vh→0.93×、14vh→0.88×、20vh→0.83×。

#### 尺寸五階與節奏

桌機 L 44vw / M+ 32vw / M 26vw / S 18vw / XS 14vw（3.14 倍落差），一排永不超過兩張，成對的用**負的 `margin-top`** 並肩。三個系列用不同的單／雙節奏：山之間 單雙單雙單、海與黃昏 雙單雙單單、城市節奏 單雙雙。

**L（44vw）一律單張置中。** 系列名只留下 21vw ~ 77vw 的乾淨帶，大圖再找一張並肩就一定會壓到英文系列名——實測就是這樣抓到的。

#### 系列名縮小、顏色壓淡

字級 `clamp(2rem, 7.5vw, 7rem)` → `clamp(1.5rem, 4.2vw, 3.75rem)`（桌機 108px → 60px）。**這是照片能放到 44vw 的前提**：108px 時「海與黃昏」佔 4~34vw、「SUNSET」佔 72~96vw，中間乾淨帶只剩 28vw；縮到 60px 後名字佔 4~21vw 與 77~96vw，乾淨帶 57vw。

顏色壓淡一階（中文 `ink` → `ink-500`、英文 `ink-500` → `ink-300`）。照片會從字面上蓋過去，深色大字被切成一半反而比淡色字更吵。字本身有 `sr-only` 的無障礙版本，畫面上那兩個 span 是 `aria-hidden` 的裝飾字。

#### reduced-motion

`--gt` 停在 0.5 ＝零位移，照片流本來就是完整可見的靜態排版，**不需要任何補丁**（舊版為了讓關掉動效時看得到第三列，得把整組拼貼 `scale(0.6)`，已隨結構一起刪掉）。只留「文字浮到照片之上並加紙色暈邊」這一項。實測所有卡片的 `transform` 都是 identity。

#### 實測

整頁 14.87 個視窗（原 10.8）。三個區塊各取 40 個捲動位置、共 329 組**水平有重疊**的相鄰照片，垂直重疊 **0 次**、最小間距 174px。大照片（>40vw）在畫面上的 63 個取樣中與系列名相交 **0 次**。手機同樣 0／0。

### 17. hero 之後那行名字

`Chenming` 靠左、`&` 正中央、`Pinyi` 靠右，**三個字在同一條水平線上**。用 `grid-template-columns: 1fr auto 1fr` 置中——`space-between` 會因為左右兩個字長度不同而把中間那個推歪（實測 `&` 落在 cx=720，正好是 1440 的一半）。

字級 `clamp(1.5rem, 4vw, 3.25rem)`（桌機 52px）。**它真正的作用是留白**，不是裝飾：hero 直接接上第一個系列區塊太擠，中間空一段捲起來才順。

### 18. hero 改成滿版出血

原本 hero 內縮一圈紙色外框（`--gallery-frame: clamp(10px, 2.4vw, 26px)`）。新人要滿版，所以把這個值改成 `0px`。

**只改這一行是刻意的**：開場動畫最後那張放大到的幾何位置（`.pl-hero` 的 `inset`）吃的是同一個變數，兩邊一起改才會在放大結束時與底下的 hero 無縫重合。圓角也改成跟著這個變數走——外框為 0 時留著圓角，四個角會露出頁面底色。要把外框加回來就只動那一行。

### 19. 按住往右拉：照片全部對齊到畫面中心軸

在**相簿首頁**的系列區塊上按住往右拉超過 90px，照片全部移到畫面正中的垂直軸、沿軸等距排開；往左拉回散落版。實測所有照片的中心點都是 720（1440 的一半），最高的一張 77dvh，**整張看得完不會被視窗裁掉**。

三件實作上的事：

- **不改 `margin` / `width`，只用 transform 位移。** 照片流本來就是一條垂直流，所以對齊只剩水平這一維：`--align-dx` ＝ `50vw - 照片水平中心`，script 端一行算完。這樣整段動畫只動 transform，符合 `creative-direction` §4「禁對 layout 屬性做 transition」，也不必為了對位去做 FLIP。
- **對齊時整組加 `--fit: 0.8` 的縮放**，讓滿畫面的大圖縮到 77dvh，整張看得完不會被視窗裁掉。`scale` 以卡片自身中心為原點，不會把剛對好的中心點推歪。
- **兩個手勢衝突要擋掉**：`draggable="false"` + `@dragstart.prevent`，不然按住照片拖曳會啟動瀏覽器原生的圖片拖放、`pointermove` 直接斷掉（實測踩到）；垂直位移大於水平時整段讓給原生捲動，手機才不會拉不動頁面。拖完那一下的 click 也要吃掉，否則會直接進系列頁。

**這個排版只有拖曳一種入口**，鍵盤與觸控使用者到不了。它是同一批照片的另一種看法，不是功能路徑——照片與系列入口都還在——所以沒有另外加按鈕。要補的話得放在連結外面（按鈕不能包在連結裡）。

### 20. 導覽收斂成右上角選單（取代底部膠囊與頁尾兩顆按鈕）

原本這頁有**兩個導覽面**，而且都有毛病：

- 底部的系列膠囊（`GalleryStickyNav`）只有捲到最後一個視窗才淡入，**中段整段沒有任何導覽**
- 頁尾兩顆 `UButton`（前往喜帖／關於我們）是**後台的元件**——實心金底、白字、`size="xl"`。整頁只有這兩個東西來自後台設計系統，旁邊全是襯線大字、紙色、金色細線。突兀的不是「有按鈕」，是一頁同時活著兩套設計語言。

兩者合併成 `PublicMenu`：右上角常駐的選單鈕，展開一份全螢幕清單（三個系列＋婚紗相簿＋我們的故事＋喜帖，**自動濾掉當前頁那一列**）。`GalleryStickyNav.vue` 已刪除。掛在相簿首頁、系列頁、故事頁；喜帖頁不掛——它整頁本身就是導覽（信封、拍立得），再加漢堡會破壞桑帖桌面的情境。

#### 互動抄 vue-bits 的 Flowing Menu，外觀不抄

滑過某一列時，一條跑馬燈**從游標進入的那一側**掃進來。原版是黑底白字、無襯線粗體，直接拿來用就是再引進一套外來語言——跟那兩顆按鈕犯一樣的錯。所以：

- 外觀換成本站語彙：紙色底、墨色字、`font-display` 襯線、`--color-line` 細線分隔
- **跑馬燈裡放該系列自己的照片**，效果本身就是內容，不是純特效
- 墨底紙字的橫帶＝相紙的負片，跟這頁的照片主題對得上
- 只用 CSS transition 與 keyframes，不引入動畫函式庫（原版用 GSAP）

換邊時要先把 `transition` 關掉一格再設 `--edge`，否則跑馬燈會從對側「掃」過整列才歸位。跑馬燈 `z-index: 2` 蓋在連結上、`pointer-events: none` 讓點擊穿透下去。

#### 三件不做會出事的事

- **跑馬燈是 hover 驅動的，觸控裝置沒有 hover。** 婚禮賓客多數用手機——這個效果大部分人看不到，手機上它退化成一份乾淨的清單。功能不受影響，但要知道買到的是什麼。
- **選單鈕沒有字也沒有底色**（新人指示，覆蓋原本「配字」的決定）。裸圖示要自己扛兩件事：語意靠 `aria-label`（「開啟選單／關閉選單」）補回來；可讀性靠紙色 `drop-shadow` 光暈——按鈕浮在 hero 滿版照片上，沒有底色就會被照片吃掉。
- **頁尾留一行純文字連結。** 選單靠 JS，JS 沒跑起來就完全沒有出口了。細字加底線的連結跟實心按鈕是兩種東西，不會再突兀。系列頁的兩顆按鈕同樣換掉。

`prefers-reduced-motion` 時不跑無限跑馬燈，滑過只換色（`creative-direction` §4）。無障礙：`aria-expanded` / `aria-controls`、開啟時焦點移到第一列、Esc 關閉並把焦點還給按鈕、Tab 鎖在「按鈕＋選單連結」之間、開啟時鎖住背景捲動。

### 21. 頁尾逐行入場

整頁每個區塊都是捲動觸發入場，只有頁尾原本是「捲到就在那裡」，看起來像另一頁貼上來的。改成眉標 → 標語 → 連結逐行升起，step 120ms。

兩個坑：

- `data-anim` 在 `onMounted` 才掛上——**沒有 JS 時屬性不存在，文字一律直接顯示**。
- 關掉動效時捲動引擎整個不啟動，`data-in` 永遠是 `false`，文字會**永遠隱藏**。要在 `@media (prefers-reduced-motion: reduce)` 裡把它救回來。
- 頁尾在文件最底，捲到底時 `travel` 進度只到 0.22 左右（元素中心永遠到不了視窗中心），門檻要壓在那之下，設 0.14。

### 22. 系列說明搬到系列名底下

原本釘在畫面正中的底部，還墊了一層 88% 的紙色膠囊。那塊底色浮在畫面中間很搶眼。

**先量再改**：三個系列各取 51 個捲動位置，記錄說明文字的矩形背後有沒有照片經過——

```
series-meadow   XXXX....XXXXXXXXX....XXXXXXXX....XXXXXXXX....XXXXX.
series-seaside  ...XXXXXXXXXXXXX.....XXXXXXXX.....XXXXXXX....XXXX..
series-city     XXXXXX........XXXXXXXXXXXXXX........XXXXXXXXXXXX...
```

三段的乾淨時段**完全錯開**，所以「只顯示一小段時間」這個做法解不掉，換一個時間窗只是換一種賭法。

改成把說明文字貼在系列名底下，並把照片帶的左緣從 17vw 推到 24vw（帶寬 66vw → 59vw，仍在 2/3 以內），讓出系列名那一塊。改完重量：三個系列整段捲動 **51/51 全乾淨**。底色塊拿掉，只留紙色柔邊光暈當保險（沒有硬邊）。顯示區間也縮短成進度 0.06~0.34，講完就讓開。

### 23. 收尾張置中、三線選單、常駐游標

新人在大螢幕上回報「最後的圖片整個靠右邊」。量到的確實如此——三段的最後一張分別落在畫面 55／74／70vw。

順手抓出一筆位置漂移：照片帶左緣在第 22 節從 17vw 推到 24vw（讓出系列說明那塊），但 L 大圖的帶內 x 只從 11 改成 7.5、少扣了 3.5，於是**每張 44vw 大圖都往右歪了 3.5vw**。註解寫的是「x=11＝畫面 28~72vw」，程式碼算出來卻是 31.5~75.5——註解記的是本意，數字沒跟上。修正成 x=4，三張大圖全部回到畫面正中。

收尾張改成單張置中（畫面 50vw）。**只改落點，尺寸與寬高比一律維持原樣**（新人明確要求海邊第七張維持原比例）。城市段原本末兩張並肩，要置中就不能再並肩，節奏改成 單 → 雙 → 單 → 單。

實測（2560×1400，47 個捲動位置）：三段收尾張中心 **全部 50vw**、三張 L 大圖中心 **全部 50vw**、相鄰照片垂直重疊 **0**、大圖壓到系列名 **0**、最小間距 293px。

游標改成兩段式：平常是一顆 9px 小墨點跟著走，滑到 `[data-cursor]` 才漲成 84px 圓牌亮出「Enter」。

一個要注意的點：**原生游標的隱藏規則搬去 `GalleryCursor` 掛在 `<html>` 的 class 上**（`gc-native-off`），不再散在各元件的 `<style scoped>`。理由是 scoped style 不管 JS 有沒有跑起來都會生效——JS 掛不上時原本會變成「原生游標被藏起來、自訂游標也沒出現」，整頁沒有游標。改由元件掛載成功才加 class，`onUnmounted` 移除，離開相簿頁自動還原。連結、按鈕自己的 `cursor: pointer` 也要蓋，所以選擇器帶 `*`。游標層 `z-index: 90`，要蓋過選單面板（65）與開關（70）。

### 24. 游標只在照片上變、選單線改白、開場字樣改成金色浸墨

**游標**：小墨點放大到 14px。`data-cursor="Enter"` 原本掛在 `.ss-link` 上——那條連結包住整個 section，所以整段捲下來游標都停在 Enter 圓牌，離開照片也不會回去。改掛到每張 `.ss-card`。

搬完還是不會亮，因為 `.ss-foot`（系列說明那層 sticky）是滿版一層、`z-index: 3` 疊在照片之上，滑鼠永遠碰到的是它。補 `pointer-events: none`——它本來就是 `aria-hidden` 的裝飾層，不接互動。實測：照片上 圓牌 1／墨點 0，離開照片 圓牌 0／墨點 1。

**選單線**：白色、無陰影（新人指示）。純白只在 hero 滿版照片上看得見，往下捲整頁都是紙色底，白線會直接消失。用 `mix-blend-mode: difference` 解：線是白的，蓋在深色照片上就是白的，蓋在紙色底上自動翻成深色。一條規則、不需要 JS 判斷捲到哪，也不用把陰影加回來。

**開場字樣**：維持原樣（沿路徑上墨、`--color-ink-700`）——試過改成由左而右的斜向羽化遮罩＋燙金色，新人看過後不喜歡漸層過場、顏色也要留黑，已還原。

留一筆給以後：新人回報「跑得不順、後面才去補邊邊」，成因是 `Union.svg` 是**輪廓化字形**，那條路徑畫的是字的**輪廓線**不是**中心線**——筆走完一筆的左緣要繞一大圈才回來走右緣，同一筆先出現半邊、隔一段才被補上另一邊。加粗筆刷不能解：粗到蓋得住一筆的寬度就會順手揭開旁邊的筆畫。要真的做出書寫感得另備一條中心線路徑，那是字型設計端的工，不是這裡能補的。

### 25. 對齊模式改成一張接一張

「按住往右拉」把照片全部推到畫面中軸，原本只算了水平位移（`--align-dx`）。散落版型裡**並肩的兩張是靠負 `margin-top` 疊上去的**——只推水平的話那個負值還在，兩張到了中軸就直接重疊。

補一個垂直分量 `--align-dy`。高度在兩種排法下完全相同（`--fit` 的縮放以卡片自身中心為原點、不影響版面），所以差額是純 vh：`i * ALIGN_GAP - 累積 gap`，`ALIGN_GAP` 取 8vh。對齊模式同時把視差關掉（`--lift: 0`）——每張速度不同的話，排成一直行還是會互相追上。

實測（桌機 1440×900 / 手機 390×844，三段各做一次拖曳手勢）：所有照片中心 720 / 195、垂直重疊 **0**、最小間距 140px / 93px、最高一張 77dvh。

### 26. 游標放大的節奏

小墨點 → 圓牌原本 250ms `ease-emphasized`，新人回報太快、很突兀。

兩件事一起改：

- **不是兩個元素硬切換，是同一顆長大**：墨點放大時跟著一起放大再淡出（`scale(6)`），圓牌則從跟墨點一樣的尺寸長起來（14 / 84 ≒ `scale(0.167)`）。狀態改由根層的 `data-state`（`off` / `dot` / `pill`）統一驅動。
- **easing 換掉，不只是拉長時間**：`--ease-emphasized` 的曲線太前傾——460ms 的版本在 120ms 就已經走完 86%，時間拉長也感覺不出來變慢。改用 `--ease-standard` 並拉到 500ms，同樣的 120ms 只走到 64%。

### 27. 回到最上方（`PublicBackToTop`）

右下角，一條細直線、頂端一個小箭頭，底下寫 `Scroll up`（10px）。沒有圓鈕、沒有底色——先做過一版圓形箭頭鈕，新人改成這個。掛在與 `PublicMenu`／`MusicToggle` 相同的三頁（相簿首頁／系列頁／故事頁）。

- **出現時機**：`scrollY > innerHeight`（滾出 hero 之後）。之前 `opacity: 0` 且 `pointer-events: none`，不佔位也點不到。

實測（1440×900 / 390×844）：hero 內與 hero 邊界皆隱藏且不可點，滾出 hero 後出現、可點，按下回到 `scrollY = 0` 並自動收起；系列頁與故事頁同樣掛上；console 錯誤 0。

> 踩到一個 Nuxt dev 的坑：**新增 `app/components/` 底下的元件檔後，client 端的 component registry 不會熱更新**。症狀是 SSR 輸出裡有那個元件、hydration 卻報 `Failed to resolve component` 並把節點整個丟掉，畫面上看不到。重啟 `npm run dev` 就好——不要以為是自己寫錯。

### 31. 海邊那段的泡泡

`public/images/story/bubble.png`（1536×1024，1.5MB）先用 `sips -c 900 900` 置中裁成正方形（原圖是 3:2、泡泡在正中間，不裁的話 `object-fit` 算出來的實際直徑對不上設定的尺寸），再 `cwebp -q 80 -resize 256 256` → `public/images/gallery-art/bubble.webp`，**21KB**。

分兩組共 18 顆，直徑 7~46px，一邊往上一邊往右偏。實測 1.5 秒內位移 dx +7~+19px、dy −74~−105px。

| 組 | 顆數 | 起點 | 行程 | 位置 |
|---|---|---|---|---|
| 環境（`AMBIENT_BUBBLES`） | 12 | 畫面下方 −14vh | 124vh | 橫跨整段 6~94vw |
| 貼人物（`FIGURE_BUBBLES`） | 6 | 50~64vh（插圖那對新人的腳邊） | 40~58vh | 15~27vw，就在插圖裡人物的右邊 |

第二組是後補的：新人要「人物的右邊也要有一些泡泡」。關鍵是**起點抬高、行程縮短**——直接沿用環境那組的參數只會變成「從畫面最底一路衝上來、剛好經過人物旁邊」，看起來不是從人身邊冒出來的。插圖用 `object-position: bottom left`，畫出來的人物實際落在 5~14vw，所以這一簇擺在 15~27vw。

三件實作上的重點：

- **位置、大小、軌跡全部寫死在表裡，不能用 `Math.random()`**。隨機值會讓 SSR 與 client 算出不同的結果，hydration 直接對不起來。變化感靠手調 12 組參數做出來。
- **`animation-delay` 給負值**，一進場泡泡就已經在半空中，不會全部從底下一起冒出來。
- **飄的軌跡不是直線**：keyframe 在 35%／65% 兩格讓 x 走得比 y 慢（0.45／0.6 倍），整段看起來會微微擺動。只動 transform 與 opacity。

泡泡層在 `.ss-stage`（`z-index: 1`），跟插圖、大字同一層，所以照片會從它們前面經過。區塊不在畫面上時 `animation-play-state: paused`，不空轉。

`prefers-reduced-motion` 下整層 `display: none`——`main.css` 的全域 guard 會把動畫壓成 0.01ms，泡泡會定格在終點（透明、飄在畫面外），留著只是死節點。

用 `series.bubbles` 旗標開關，目前只有 seaside 是 `true`；實測 meadow／city 各 0 顆、seaside 12 顆。

### 32. 草原那段的風車

`public/images/story/windmill.png`（1295×1214，1.15MB）→ `sips -c 1214 1214` 裁成正方形（轉軸要在元素正中央，`transform-origin: center` 才不會轉出偏心）→ `cwebp -q 82 -resize 256 256` → `public/images/gallery-art/windmill.webp`，**12.7KB**。

兩支，右上 44px、左下 36px，各自轉速不同（11s／6.5s），站在插圖那對粉色新人的左邊。右上那支落在人物頭頂的左上方（新人在截圖上點的位置），另一支在它左下方。尺寸與間距調過三輪：兩支要**大小接近、位置也靠近**才像一組，落差拉大就變成兩個各自為政的裝飾。

**進場跟著人物走**：第一版風車一直掛在畫面上，人物還在淡入它就已經在那了。改成綁 `data-active`（跟插圖同一個旗標）並加 220ms 的 `transition-delay`，順序變成 人物 → 風車。退場不延遲。進場只能動 `opacity`——`transform` 已經被自轉的 `animation` 佔用，兩邊會打架。實測進度 0.09 時插圖 0.88、風車才 0.04，0.14 時風車 0.93。

**位置是量出來的不是猜的**：插圖用 `object-position: bottom left`，但圖檔本身四周有透明留白，所以「框」是 4~24vw、**畫出來的人物實際只落在 7.9~21.4vw**（用 canvas 掃 alpha 量的）。左邊那條 0~7.9vw 才是真正空著的地方，風車就擺在那裡。`bottom` 沿用插圖的錨點（`50% + 3rem`）往上下推，兩支跟插圖對得起來。

兩個踩到的點：

- **`@keyframes` 只寫 `to { rotate(360deg) }` 會變靜止**——0deg 與 360deg 的矩陣完全相同，瀏覽器退回矩陣插值就不轉了。`from`／`to` 都明寫角度才會逐格轉（`MusicToggle` 的金唱片同一個坑）。
- **轉起來佔的是「旋轉後的外框」＝邊長 × √2**，比設定的寬度大四成。手機左邊那條很窄，`left` 沒留夠的話轉到 45 度時左半邊會被 `.ss` 的 `overflow-x: clip` 切掉。實測後桌機 `left: 1.2vw`／手機 `left: 2vw`。

`prefers-reduced-motion` 下 `animation: none`——風車不轉就是一張靜態插圖，留著沒問題，但要真的停在 0 度，不能靠全域 guard 把時間壓成 0.01ms（那會停在隨機角度）。

用 `series.windmills` 旗標開關，目前只有 meadow 是 `true`；實測 meadow 2 支、其他兩段 0 支，桌機／手機都會轉。

### 33. 玫瑰花瓣灑落（`GalleryPetals`）

`public/images/story/rose-1~3.png`（各約 2MB）→ `public/images/gallery-art/rose-1~3.webp`（`cwebp -q 82`、寬 192px），三張合計 **5.9MB → 15.8KB**。14 片，寬 13~34px，三張花瓣輪流用。

**它是頁面層級的固定圖層，不是掛在系列區塊裡。** 一開始做在城市那一段的 `.ss-stage` 內，新人要「花瓣一直掉到頁尾」——掛在區塊裡的話區塊一捲完花瓣就跟著離開，到不了頁尾。改成 `position: fixed` 的 `GalleryPetals`，由 `anchor="series-city"` 決定何時開始灑（該區塊進畫面兩成），之後一路到底都不關。`z-index: 40`：壓在照片之上（花瓣落在畫面前方才像灑下來），在所有介面元素之下（音樂鈕 50、選單 65/70、游標 90）。

**一片花瓣拆成三層**，因為落下、左右搖、自轉三個動作都要動 `transform`，放在同一個元素上只有最後一個 `animation` 會生效：

| 層 | 動作 | 節奏 |
|---|---|---|
| `.gpt-fall` | 往下掉 + 頭尾淡入淡出 | `linear infinite`，12~25s |
| `.gpt-sway` | 左右搖 | `ease-standard infinite **alternate**`，3~6.4s |
| `.gpt-art` | 自轉 | `linear infinite`，6~14s，一半反向 |

搖擺用 `alternate` 是關鍵：兩端各停一下才像被風托著，不是等速平移。自轉的 `@keyframes` 同樣 `from`／`to` 都明寫角度（只寫 `to` 會退回矩陣插值而變靜止）。

實測（1440×900）：hero 與海邊段圖層 `opacity: 0`、動畫暫停；城市段與頁尾 `opacity: 1`、畫面上 13~14 片；1.2 秒內位移 dy +69~+114px。`prefers-reduced-motion` 下整層 `display: none`。

### 34. 頁尾收尾句：手機三行、不帶標點

文案「照片**留下**了瞬間，但最美的風景，是那天有你們在場。」（原本是「收錄」，`content.title` 的「收錄我們相愛的樣子」一起改成「留下」）。

手機一個子句一行、標點收掉；桌機維持完整一句。做法是**同一份 DOM 兩種排法**：句子在 script 端依「，」拆成子句（`FULL_STOP` 先去掉句尾句號），每個子句一個 `.gp-clause`、標點包在 `.gp-punct` 裡。手機 `.gp-clause { display: block }` + `.gp-punct { display: none }`，`min-width: 640px` 再還原成 `inline`。

不用兩份文字互相 `display: none` 的原因：那會讓螢幕閱讀器唸到兩次。現在 `textContent` 永遠是完整的一句「照片留下了瞬間，但最美的風景，是那天有你們在場。」，只是標點在手機上看不到。

實測：桌機 1 行、標點 `inline`；手機 3 行、標點 `none`、看到的字沒有標點，唸出來仍是完整句子。

> 三隻貓（`story/cats.png`）試放在頁尾插圖右下角，新人看過後覺得不搭，已整組移除（元件、型別、內容欄位、`gallery-art/cats.webp` 都清掉）。原始 PNG 留在 `story/`。

### 35. 選單縮圖改用專屬欄位，只准填橫式

新人回報「城市和喜帖用的圖會裁切到人物，應該用不會裁切到的橫式照片，兩者要不一樣」。

**根因是縮圖沿用了別處挑的圖。** 選單那一列的縮圖是 `aspect-ratio: 3/2` + `object-fit: cover`，但圖是借來的——三個系列列吃 `series.preview`（為系列頁滿版預告卡挑的）、喜帖列吃 `series[2].preview`。城市系列的 10~14 **全是直式**（1111×1600），3:2 置中裁切只留中間 46% 那一條，頭跟腿都會被切掉。喜帖借的是同一張（13），所以兩列不但都切到人，還長得一模一樣。

**判準：橫式只有 01~09。** 量過全部 33 張，01~09 是 1600×1111（比例 1.44）、10~33 是 1111×1600（0.69）。1.44 裁成 1.5 只修掉上下各 2%，人一定完整；0.69 裁成 1.5 必砍頭。所以縮圖的可選池就是 01~09 這九張，不是憑檔名或系列歸屬挑。

挑法是把九張真的裁成 3:2 縮到 256px 逐張看過，再選「主體居中、兩張臉夠大、縮到 64px 還認得出人」的：

| 目錄列 | 換前 | 換後 | 為什麼 |
|---|---|---|---|
| In the City | 13（直式） | **04** | city 系列自己沒有橫式照片，只能借。04 兩張臉最大又壓在正中央，縮到 64px 仍看得出是誰；彩色光斑也讓這一列不跟上面的海邊列撞調性 |
| 喜帖 | 13（直式） | **09** | 手捧發光的 LOVE 字燈，主體與兩張臉都在中央，頭頂還留得住白邊。「LOVE」本身就是喜帖語彙，且與 04 的日光近拍完全不同調 |

其餘四列（In the Wild 02／By the Ocean 07／婚紗相簿 01／我們的故事 06）本來就是橫式，實測裁切後人物完整，**沒有動**。

**防再發的作法**：`GallerySeries` 加 `menuThumb`、`GalleryContent` 加 `inviteThumb`，選單只吃這兩個欄位，不再共用 `preview` 或 `cover`。`preview` 現在只服務系列頁的「下一個系列」卡片，日後有人為了那張卡片改成直式照片，也不會再連帶把選單縮圖弄壞。

實測（1440×900 / 390×844，相簿首頁與系列頁各拍一次，把跑馬燈強制拉到定位截圖）：六列縮圖的人物全部完整、無切頭切半身，City 與喜帖兩列已是不同照片。

### 37. 照片流的圖先佔位（PR #159 Copilot 審查第二輪）

`GallerySeriesFlow` 的 `<img>` 原本只有 `width: 100%; height: auto`，沒有原始寬高——lazy 圖載入前高度是 0，載完才撐開。實測 1440×900 的 meadow 系列頁：圖都還沒到時照片流只有 3456px 高，全部載完是 21694px，25 張一路從 0 撐開，捲動中會跳，`useScrollProgress` 快取的位置也會失準。`GalleryPhoto` 加 `width`／`height`，由 `useGalleryContent` 的 `photoSize()` 算（第一批 1600×1111、第二批 1566×1044，依 `LANDSCAPE` 決定直橫，34／44／50 三張新人裁過的用實際尺寸），`<img>` 帶上這兩個屬性後瀏覽器載入前就依比例佔位。實測載入前後每張高度與整條照片流高度完全相同，最終版面與改前一致。

同一輪 Copilot 另一條「系列頁切上一組／下一組時內容殘留」實測是誤判：Nuxt 的 `NuxtPage` 預設用帶入參數後的路徑當 key，`/gallery/w/meadow` 換到 `/seaside` 會重新掛載；站內導覽點下一組，標題、首圖、照片流、上下組連結與分頁標題都跟著換。
