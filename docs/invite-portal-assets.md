## C. 設計決策記錄

### 1. 信封的熱區在「信封前片」而不是愛心卡

視覺上愛心卡插在信封裡（`envelope-front` 疊在它上面），而**圖片的透明像素一樣攔截點擊**——熱區若放在愛心上會永遠點不到。因此熱區改掛在最前面的 `envelope-front`，並用 `InviteStage` 的 `:has()` 規則讓同組（`group: 'envelope'`）的愛心卡在 hover／focus 時一起浮起一截。

結果：滑鼠點信封任一處都有效、鍵盤只有一個 Tab 停留點、螢幕閱讀器聽到一個連結「我們結婚了！打開喜帖，看我們的故事」。

### 2. 動效超出 creative-direction §4「一頁最多一個主動效」——刻意延伸

入口頁同時有進場 stagger、滑鼠視差、持續漂浮。判定上視為**單一敘事語彙**（「喜帖桌面甦醒」）：進場是開場、視差與漂浮是同一語彙的環境層。

§4 的三條硬原則未破：
- reduced-motion：`InviteStage` 以 `matchMedia` 關閉視差與漂浮（實測：漂浮元素數 0、進場層 opacity 1），CSS 全域 guard 另行兜底
- 只動 transform／opacity：無 layout 屬性 transition，無 `transition-all`
- duration 與 ease：transition 走 250ms／400ms ＋ `--ease-standard`／`--ease-emphasized`；持續漂浮是 9~28 秒的環境級 keyframes，不屬於互動 transition

`SceneFloat` 目前四種語彙：`ribbon`（左右擺盪 9s）、`leaf`（緩降 11s）、`petal`（飄移 13s）、`spin`（金唱片自轉 28s）。前三種靠 `animation-delay: calc(var(--i) * -Ns)` 用 `order` 錯開相位，同語彙的物件才不會整齊劃一地動。

`spin` 有個 CSS 陷阱值得記：整圈旋轉的 keyframes **必須把 `from` 與 `to` 都寫出來、且兩幀用同一組 transform function**（只有角度不同）。只寫 `to { transform: … rotate(360deg) }` 的話瀏覽器要在「元素現有的 transform」與「目標 transform」之間插值，兩邊 function 列表不同會退回矩陣插值——而 0deg 與 360deg 的矩陣完全相同，整個動畫會變成靜止不動。

### 3. 手機不做陀螺儀視差

iOS 的 `DeviceOrientationEvent.requestPermission()` 需要 user gesture，開場跳權限彈窗會毀掉儀式感。觸控裝置（`(hover: hover) and (pointer: fine)` 不成立）改以持續漂浮代替。

### 4. 不做離場轉場

Nuxt 的 `pageTransition` 由「即將進入的路由」決定，要讓離開入口頁時淡出得改全站設定，會波及後台（違反「後台動效安靜」）。改以按下時的 `scale(0.99)` 即時回饋代替。

### 5. 兩組座標用純 CSS 切換

桌機／手機座標都寫成 CSS 變數，由 media query 選用，**不靠 JS 判斷斷點**——SSR 與 client 首渲染完全一致，沒有 hydration mismatch 風險，也沒有換版閃動。

### 6. 主標出圖／出 SVG 而非用 web font

「Alex & Lele」與花體「Wedding Invitation」是設計稿的字體資產，web font 重現不了。名字與花體各自是獨立 SVG，能各自進場；`alt` 給完整文字保住 a11y 與 SEO，同時避開 `scripts/visual-hierarchy-check.mjs` 不把 `app/components/` 當公開頁的字級限制。

### 7. 底色沿用品牌 token，不還原設計稿的中性灰

設計稿底色是中性灰白（約 `#EEEEEE`），專案品牌底色是暖白 `paper #FAF7F1`。依 creative-direction §0「品牌恆定層全域唯一、前台不另設色板」，這裡採用 `bg-paper`；並排才看得出色溫差，單獨瀏覽無損，且與 `/story`、`/gallery` 連貫。要完全忠於稿子的話，改 `InviteStage` 根節點的 `bg-paper` 即可。

### 8. 進場改成三幕：信封 → 愛心卡滑出 → 其餘場景由外而內收攏

`lace-heart` 用 `entrance: 'slide-up'`（`SceneItem` 型別），取代通用的單拍上浮：`opacity 0 + translateY(11%)` → 終態，`translateY` 用 `%`（相對自己渲染高度）不用 px，桌機／手機不必分別調參數。

整場進場再切成三幕，靠新增的 `phaseDelay?: number`（毫秒）疊加在既有的 `order*70ms` stagger 之上：

| 幕 | 物件 | 起跑時間 | 時長 |
|---|---|---|---|
| 1 | 信封三層（`envelope-back`／`envelope-inner`／`envelope-front`，`order:0`） | 0ms | 400ms |
| 2 | `lace-heart`（`phaseDelay:300`） | 300ms（信封落定前後） | 800ms |
| 3 | 其餘全部物件（標題、拍立得、緞帶、花、貼紙、鋼筆…） | `phaseDelay: SCENE_DELAY`（900ms）+ 各自 `order*70ms` 錯開 | 各 400ms |

第三幕的 `order` 不是隨手編的，而是**離視覺中心（信封／愛心）由遠而近**：最外圈的銀杏葉、花瓣、鋼筆墨水先落定（order 1~4），接著標題組（5~9，內部照 Alex → & → Lele → Wedding → Invitation 的閱讀順序，不拆散），再來緞帶與花（10~13），最後才是貼在信封旁的日期貼紙、金唱片、兩張拍立得與蠟封（14~16）。視線被一路帶往中央的主要熱區，全場約 2.4 秒收完。

**三個踩過的坑**：

1. **opacity 不能拿掉**：試過改成純位移（不淡入，靠 z-index 被信封前片天然遮住），結果卡片在 delay 期間就以完全不透明、卡在信封裡的低位置浮在頁面上——因為沒有 opacity 動畫時，它的透明度從一開始就是 1，不會等信封先出現。淡入＋位移的組合版本才是對的。
2. **`--ease-emphasized` 讓 duration 名不符實**：`si-reveal-up` 原本沿用其他物件的 `--ease-emphasized`，這條曲線在時間軸 45% 處就已經跑完 94% 的位移（`cubic-bezier(0.05,0.7,0.1,1)` 前段極陡），等於整段 duration 有大半時間卡片其實已經定格不動，只是動畫技術上還沒結束。改用 `linear`——刻意的例外，其他物件仍用 `--ease-emphasized`。
3. **起始位移不能太低，否則淡入時會露出信封外**：起點越低越像「從信封深處抽出來」，但卡片下緣一旦低過信封前片的下緣就會穿幫。兩個斷點各自算過上限（桌機 12.5%、手機 11.0%），取 **11%**。
   > 更早的版本用的是另一種解法：起點放到 42%，靠 `0~65%` 維持 `opacity:0`、`65.001%` 瞬間把 transform 補到 14.7%（此刻仍全透明，看不見這個跳躍）、`65~85%` 才淡入。技術上可行，但那 65% 是**純粹的空轉**——卡片既看不見也沒在動，2 秒的 duration 有 1.3 秒是死時間，使用者的感受就是「信封出現後等很久愛心才出來」。改成短 duration + 安全起點後，這段 keyframes 跳躍就不需要了。

時序驗證用 Web Animations API 逐格 scrub `currentTime`（暫停動畫、手動設定時間點截圖），比等真實時間可靠——dev server 的 SSR／hydration 開銷本身就會吃掉數百毫秒，用 wall-clock `waitForTimeout` 對時序容易誤判。要看整體節奏則反過來用連續 reload + 固定時間點截圖拼 filmstrip，那才反映使用者真正看到的速度感。

### 9. `ribbon-top` 用水平鏡射而非旋轉，且鏡射是「逐斷點」的

素材本身的走向（細端左上、燕尾右下）跟桌機稿相反（細端要在右上、燕尾在左下），這是鏡像關係不是旋轉關係——用 `rotate()` 怎麼轉都對不出正確的螺旋手性。套用 `scaleX(-1)`（實作用 CSS var `--flip` 乘進 `scale()`，float keyframes 也要帶上避免鏡射被漂浮動畫覆蓋掉）。

後續校正手機稿時發現**兩張稿的緞帶走向剛好相反**：手機版要的是素材原始方向，不鏡射。所以 `flip` 從 `SceneItem` 移到 `ScenePlacement`（與 `rotate` 同層級），CSS 也比照 `--rot` 的做法拆成 `--d-flip`／`--m-flip`，由 media query 切換。教訓：任何「素材方向」的調整都是斷點層級的屬性，不是物件層級的。

### 10. 標題圖層曾經對螢幕閱讀器完全隱形

`InviteObject.vue` 的 `<img>` 曾寫死 `alt=""`，場景資料裡設定的 `alt`（如 `title-alex` 的 `'Alex'`）從未真正渲染到 DOM；外層 `.si` 的 `aria-hidden` 又是用 `item.to`（有無熱區）判斷，導致六張標題圖全被判定為「純裝飾」蓋上 `aria-hidden="true"`——螢幕閱讀器完全聽不到「Alex & Lele」這個頁面標題，即使決策 #6 早就寫了「alt 給完整文字保住 a11y」，實作卻沒接上。

修法：`<img>` 改 `:alt="item.alt"`，`aria-hidden` 判準從「有沒有熱區」改成「有沒有 alt 文字」（`item.alt ? undefined : 'true'`）——這樣裝飾物件（`alt: ''`）維持隱藏，熱區與純標題物件都會曝光。順便拿掉重複的 `sr-only` span：熱區連結包住一張有 `alt` 的圖片時，連結的 accessible name 本來就會取自圖片 `alt`，不用再手動複製一份文字。

### 11. 手機版整體重新校正——素材與設計稿是 1:1 像素對應

手機版原本是目測填座標，實際跟稿子差很多（花束、緞帶、銀杏、拍立得、光碟、印戳全部偏小或偏位）。第二輪改用「把設計稿當底圖疊上去」的做法校正，過程中發現一件關鍵事實：

> **每個去背素材在手機稿裡就是它自己的原始像素尺寸**（手機稿寬 804px）。也就是 `mobile.w` ＝ 素材原始寬 ÷ 804 × 100，不需要目測。

驗證方式：拿 `flower-single` 上那片銀杏葉當基準點，量它在稿子裡與在素材裡的像素尺寸，比值是 1.000／0.988。`ginkgo-02`（173px → 21.5%）、`flowers-right`（311px → 38.7%）、`polaroid-beach`（477px → 59.3%）等十餘個物件的模板比對結果都落在這條規則上。**例外是掌印與花瓣**——設計稿裡另外縮過（掌印縮到 0.5~0.85），所以這幾個仍需個別量測。

剩下的位置則用模板比對自動求解（`.claude/tmp/match*.mjs`，Playwright 開一個 canvas，把素材以候選位置畫上去跟設計稿逐像素比對，取「容差內像素比例」最高者）。三個踩過的坑：

1. **評分會偏袒小樣板**：自由縮放搜尋時，信封、光碟這類大面積平坦物件會把樣板縮小、藏進一塊均勻的米色區域拿到假高分（信封縮到 52% 竟拿 0.92）。修法是改成「在最高分 93% 以內的候選裡取最大尺度」；後來確立 1:1 規則後直接固定尺寸只搜位置，問題自然消失。
2. **低對比物件要另外處理**：金色花體字（`Wedding.svg`、`ampersand.svg`）筆畫細、邊緣半透明，用 `alpha >= 200` 過濾後取樣點不足會直接判定無解，要放寬到 `alpha >= 70`；再對不上的（`Invitation.svg`）就回到疊圖目測。
3. **決策 #11 舊版的「比例換算法」是錯的**：原本用桌機版的層間偏移比例去推手機版，前提是「兩張稿的圖層相對關係一致」——實際上設計師在兩張稿裡各自縮放了圖層（桌機版愛心卡比信封小，手機版愛心卡比信封寬），這個前提不成立。跨斷點只能各自對各自的稿量，不能推算。

校正後手機版與設計稿以 50% 透明度疊圖已無可見重影。設計稿暫貼在 `public/_ref-mobile.jpg` 供 dev server 讀取，校正完已移除（要再校正時重新複製一份即可）。

### 12. 桌機版重新校正——同一套疊圖法，但縮放規則跟手機稿不同

使用者回報桌機版直式拍立得太小，比對後發現整張桌機稿的物件都偏小偏位（不只拍立得）。用跟 §11 相同的疊圖 + 模板比對重做，結論：

- **桌機稿雖然也是 1440×1024（與舞台同尺寸），但素材不是 1:1**。多數物件是**原始尺寸的 0.70 倍**（拍立得、日期貼紙、鋼筆、蠟封、金唱片、信封三層都落在 0.694~0.71），少數被設計師個別縮放過（`flowers-left` 0.50、`ink-bottle` 0.49、`flower-single` 0.52、`petals` 0.52、`ribbon.webp` 0.80、`star-moon-sun` 0.41）。所以桌機**不能照搬手機的 1:1 規則**，每個物件仍要各自量。
- 直式拍立得 `polaroid-forest` 16.5 → **21.0**（0.703 倍，正是那條 0.70），愛心卡 22.4 → **29.3**，其餘物件多半也放大 1.1~1.4 倍。

**新增的三個判定工具**（`.claude/tmp/`，皆為臨時腳本、不進版控）：

1. **疊圖試驗（最可靠的仲裁）**：把素材以候選座標半透明疊回設計稿，對得上就「合體」、對不上就出現重影。判讀時盯**素材自身帶的文字或圖案**（愛心卡的「我們結婚了！」、拍立得的照片內容）——這類高頻細節只要差 2% 就看得出雙影，比看輪廓準得多。模板比對給了幾個高分但錯誤的答案（愛心卡 35.8、信封前片 57.8/27.4），都是靠這個試驗推翻的。
2. **半透明素材要先合成再比**：`ribbon-top.webp`／`ribbon.webp` 的 alpha 上限只有 214／219（設計師把圖層透明度調低了），拿原始 RGB 去比等於整片顏色都偏。要先 `src×α + 底色×(1−α)` 合成再比對；沒發現這件事之前，緞帶的比對分數一直在 0.2~0.5 徘徊。
3. **色彩基準點反推**：信封的米色在稿子裡幾乎與背景同色，模板比對必失敗。改用**綠色內襯的尖角**當唯一基準點（素材與稿子的綠色 RGB 完全一致：173,172,150），量出尖角在稿子的位置後，配合已知寬度反推整層的中心。同一招在手機版是用銀杏葉當基準點。

**兩個回頭才發現的錯**（都靠與設計稿並排截圖抓到，不是靠比對分數）：

- **信封前片被放太高**，V 形開口壓在愛心卡中間，把卡片下緣連同「open」記號整個蓋掉——畫面上就變成「愛心從信封上緣滿出來」。正確判準是設計稿裡**「open」記號要看得見**：前片的 V 形谷底必須落在愛心尖端下方。改用素材自身的幾何反推（`envelope-front` 的 V 谷底在素材高度的 0.450 處、兩肩在 0.021 處），對到稿子量到的谷底位置 y≈37.6%，得出 `y: 38.6`（原先 33.3 → 一度誤改成 31.5，都太高）。順帶把三層寬度改成同一組比例（23.5／22.8／24.4），信封上緣（信封蓋底部 30.2%）與前片兩肩（29.3%）剛好接上。
- **左上花束的 z 低於緞帶**，緞帶從花莖前面壓過去；稿子裡是緞帶穿過花束後方。把 `flowers-left` 的 `z` 從 12 提到 24（它 `mobile: null`，只影響桌機）。

順帶修掉引言區塊：位置對齊稿子（`left` 29.5%→33.9%、`top` 59%→58.2%），英文簽名行從 `text-overline uppercase` 改成 `font-display text-body-l tracking-widest` 的大小寫混排（稿子就是混排且字級較大；沒有更接近的字級 token，維持 18px 不用任意值）。另外把它的 `animation-delay` 從 140ms 改成 2540ms——原本它會在信封還沒演完就先跳出來，與 §8 的三幕編排不一致。

### 13. 信封三層是一個剛體——手機的層間位移不能各自校正

使用者回報手機版「綠色方塊太上面了」：綠內襯（`envelope-background.webp`，一塊純色矩形）的下緣停在信封前片 V 形谷底**上方**，兩者之間露出一條背景色的縫。

根因是校正方法用錯了。§11 的做法是每個物件各自對稿子做模板比對，對散落的裝飾物件沒問題，但信封三層在設計稿裡是**同一個剛體**——它們的相對位移由素材幾何決定，一旦各自獨立微調就會拆開。實際數字：桌機的「前片中心 − 信封蓋中心」相對信封蓋寬度是 0.611，手機卻是 0.530，差了 13%。

修法是把桌機（已用 §12 的幾何反推校正過、且使用者確認過）的層間位移換算到手機：

```
層間位移（素材像素）= 桌機位移 px ÷ 桌機縮放比 0.7065
手機位置 = 手機信封蓋位置 + 層間位移 ÷ 804（手機稿 1:1）
```

得到 `envelope-back (49.1, 29.4)`、`envelope-inner (49.3, 42.4)`、`envelope-front (49.6, 46.2)`（原本三層都寫 47.8，內襯 y 是 36.0——低了 6.4%，就是那條縫）。

**兩個交叉驗證**（值得記下來的手法）：

- **獨立基準點驗算**：手機的信封蓋位置改用「綠內襯三角形的兩條斜邊」定位——素材與手機稿的綠色 RGB 完全一致（173,172,150），斜邊斜率也一致（−1.33 px/row，再次確認 1:1），量三個不同高度的左緣就能解出唯一位移 `(dx, dy) = (155, 343)`。
- **用沒動到的物件反推**：`lace-heart` 的手機座標是先前獨立校正的。拿桌機的「愛心 − 信封蓋」位移去推它，用**舊**信封蓋位置算出 `(44.5, 36.6)`、用**新**的算出 `(45.8, 35.4)`——後者與既有值 `(45.8, 35.6)` 差 0.2%。等於愛心卡自己證明了新的信封位置才是對的。

判定「有沒有縫」不必靠肉眼：`envelope-front` 的 V 谷底在素材高度 0.450 處，內襯下緣必須低於它。這條算式兩個斷點都成立才算過。

### 14. 右側葉影只給桌機，且素材的硬切斜邊必須先羽化

設計稿右緣本來就有一片葉影（左上那片的對側），使用者補了 `bg-right-shadow.png`（1416×2048，最大 alpha 只有 52，等於全圖不超過 20% 不透明度）。兩個實作重點：

**只在桌機出現。** 手機稿的右緣整條被信封與拍立得佔滿，沒有留白可以放葉影，貼上去只會把物件蒙灰。所以走 `display: none` ＋ `@media (min-width: 1024px)` 顯示，與其他斷點切換一致（純 CSS，無 hydration 風險）。

**素材左側是一條硬切的斜邊，直接貼會出現一道直線接縫。** 這是 Figma 匯出旋轉矩形留下的邊：alpha 從 0 直接跳到 26~42（換算成畫面上約 12 個亮度階），肉眼看得出來。解法是轉檔時沿著那條線做羽化——量四個 y 的邊界 x 解出直線 `x = 676 − 0.3063(y − 100)`，往右 200px 內把 alpha 線性拉起。順帶把全透明區的 RGB（原本是 0,0,0）填成有效區平均色 `#DDDDDD`，避免縮圖時黑色滲進半透明邊緣。

驗證用 A/B 截圖相減（開／關這一層各截一張，相減後看陰影自己的梯度）：最深處只讓底色暗 17 個亮度階、**相鄰像素最大階躍 4**——沒有任何階梯邊。這比「肉眼看截圖」可靠，因為 20% 不透明度的接縫在原圖上幾乎看不見，要拉 10 倍對比才現形。

尺寸取 708×1024（1× 而非 2×）：把 708 上採樣到 1000 再與真 1000 的算圖相比，alpha 最大差 7、平均 0.6（換算亮度差 2.3／0.2 階）——柔邊陰影的空間頻率遠低於取樣極限，2× 是純浪費。`cwebp -q 78 -alpha_q 60` 得 66KB，比左側那張還小。

擺放用 `height: 100%; width: auto; right: 0; top: 0`：素材上／下／右三邊都是硬切邊，只有貼齊視窗邊緣才不會露出接縫，所以不能改用寬度定尺寸（視窗一高就會在下緣露邊）。

### 15. 引言兩行改用 Noto Serif TC —— 品牌字體家族多了一支中文襯線

使用者指定引言（「兩個獨立運行的星球／在漫長時光裡，找到彼此的軌道」）用 **Noto Serif TC 16px Light、行高 200%**。三處改動：

**為什麼不開 `@theme` 字級 token**：16px 落在 `text-body`(15px) 與 `text-body-l`(18px) 之間，200% 行高也與整套 token 的 1.7 不同。為一處編輯性排版在全域字級表插一級，只會讓 `visual-hierarchy.md` 的層級表多一個沒人會再用的尺寸。寫在 scoped CSS 就地解決，也不觸發 `visual-hierarchy-check.mjs` 的任意值字級規則（該規則只掃 Tailwind class 字面值 `text-[Npx]`）。

### 16. 開場：先給一封封蠟的喜帖，點過才進桌面

使用者要求「一進入這個頁面應該要有一個點擊信封的畫面，點擊之後信封打開才會進到這個畫面」。做成同一路由內的一層開場（`InviteIntro`），不另開路由——它不是一個獨立的頁面，是這一頁的第 0 幕。

**不鋪底色**。開場層是透明的，葉影與紙紋照舊透出來；點下去之後只有「桌上的東西出現了」，不是換場。這讓兩幕在視覺上是同一個空間。

**桌面在開場期間是暫停的，不是還沒掛上去**：

```css
.is-waiting :deep(.si-enter), .is-waiting :deep(.si-art), .is-waiting :deep(.invite-tagline) {
  animation-play-state: paused;
}
```

進場動畫是 `fill: both`，第 0 幀就是 `opacity: 0`，所以暫停＝整片看不見。用 `v-if` 會讓 27 張圖等到點擊後才開始下載，進場就變成一片空白慢慢補圖。舞台另外掛 `:inert`，否則開場時 Tab 會走進看不見的 `/story`、`/gallery` 連結。

**「打開」怎麼演**：素材是一張已經封好的平面圖，沒有可以掀開的封口圖層。所以不演掀封口，改用鏡頭穿過去——先後縮蓄力（22% 處 scale 0.94），再放大到 2.4 倍淡出，950ms。提示文字先收（220ms），銀盤晚一拍才退（140ms 延遲、480ms 淡出），讓信封當主詞；同時消失的話看不出是誰動了。

**兩幕不能重疊**（第一版做錯，使用者回報「打開換場的太快了，後面畫面會出現，看起來很怪」）：初版讓桌面在點擊當下就解除暫停，於是封蠟信封還在放大、桌上的東西已經從它後面浮出來，讀起來像兩張圖疊在一起而不是一個動作。改成 `.is-waiting` 的條件由 `phase === 'intro'` 放寬到 `phase !== 'scene'`——離場整段演完（1050ms）桌面才開始。信封的 opacity 也從 78% 改成 88% 才歸零，不然中間會空一大段白紙。定案節奏：0ms 點擊 → 950ms 信封穿過去 → 1050ms 桌面開演 → 約 3.5s 全部落定。

reduced-motion 下離場動畫被全域 guard 壓成 0.01ms，所以那顆 `setTimeout` 要一併判斷：不然使用者會盯著一張空白紙一秒。

**音樂不必另外處理**。`InviteStage` 上那個 `once + capture` 的 window click 監聽本來就是為了繞過自動播放限制而存在的，開場這一下點擊正好就是它等的第一個使用者手勢——`enterScene()` 不重複呼叫 `tryPlayMusic()`。

**每次進站都會重播開場**（沒有記憶「看過了」）。從 `/story` 按上一頁回來也會再看一次。要改成只播一次的話得存 client-only 狀態（sessionStorage），那是 hydration 風險，得包在 `onMounted` 裡——目前判斷儀式感值得這個重播，先不做。

**信封寬過盤子（新人要求「再大一點，超過盤子一點」）**：`76%` → `114%`（桌機 354px 盤 vs 417px 信封，每側超出 32px）。踩到兩個坑：

- **Tailwind preflight 的 `img { max-width: 100% }` 會把它夾在盤子寬度上**，`width` 寫多少都只到 100%。第一次改完量出來還是 100%，以為是熱更新沒生效。要加 `max-width: none`。
- **溢出的兩側落在 `<button>` 的框外，點不到**。`.intro-hit` 的尺寸由裡面的銀盤決定，信封是 `position: absolute` 不撐大它。用不影響版面的 `.intro-hit::after { inset: -2% -14% }` 把可點範圍補到信封的實際邊界（已用 `elementFromPoint` 驗過兩端都命中）。

**素材**：`plate.png`（1024×1536）→ `tray.webp` 720 寬 q72 170KB；`envolope.png`（1536×1024，檔名原本拼錯）→ `envelope-sealed.webp` 900 寬 q88 65KB。銀盤是唯一超過 150KB 的素材：它是金屬拉絲紋理，WebP 對這種細噪點壓不下去，而它又是整站第一眼看到的主體，降到 620 寬（130KB）會在 retina 上糊掉。

### 17. 桌機標題組整組放大 1.22 倍，並左移 2.5%

### 18. 開場鋪滿花藝底圖——alpha 壓進 RGB 換來 5 倍體積差

使用者補了 `backgrong.png`（1536×1024，白玫瑰／尤加利／灰綠緞帶／戒枕／蠟燭圍成一圈、中間留空的平鋪照）當開場背景。中間那塊空白正好是銀盤的位置。

**節奏**：提示（220ms）→ 銀盤（140ms 延遲、480ms）→ 底圖（200ms 延遲、700ms，900ms 收乾淨）一層一層退，最後只剩信封往前穿過去；桌面 1050ms 才開演。底圖是最後才溶掉的，所以觀眾看到的是「這個世界化開，露出桌面那層紙紋與葉影」。

**轉檔關鍵：把 alpha 壓進 RGB。** 原圖是半透明的（中央 alpha 約 90~180、四角 120~146），要靠透明度疊在 `--color-paper` 上。但 WebP 的 alpha channel 在這種大面積連續漸層上非常貴：

| 設定 | 體積 |
|---|---|
| `-q 80 -alpha_q 70` | 125KB（alpha 誤差 max 10） |
| `-q 80 -alpha_q 78` | 301KB |
| `-q 80 -alpha_q 90` | 445KB |
| **先壓平到 `#FAF7F1` 再 `-q 86`（無 alpha）** | **85KB，且數學上完全等價** |

等價的推導：帶 alpha 時，元素 opacity 為 `o` 的合成結果是 `paper*(1 − o*a) + C*o*a`；先壓平成 `F = paper*(1−a) + C*a` 再套 opacity `o`，得 `paper*(1−o) + F*o`，展開後同樣是 `paper*(1 − o*a) + C*o*a`。**完全一樣**——所以連離場淡出都不會有色差。前提是這張圖永遠只疊在 paper 底色上、底下不會有別的東西透出來，這一頁成立。

**手機版是 `object-fit: cover` 的先天損失**：素材是 3:2 橫幅、裝飾全長在左右兩側，390×844 直式螢幕 cover 後會裁掉 57% 的寬度，花與戒枕基本上全被切掉，只剩中央那片米白布紋。仍然比純色底好，但要在手機上看到花藝就得另外出一張直式構圖的稿——**同一張圖沒有任何裁法救得回來**（裝飾在最外緣，任何直式裁切都會切到）。

### 19. 拍立得 hover：晃一下 ＋ 手寫對話框

使用者要「hover 拍立得的時候左右晃一晃，拍立得上面要寫『借你墨鏡😎，我們要放閃了！』」。

**晃動掛在 `.si-link`（連結層），不是 `.si-art`（圖片層）。** 圖片層的 `transform` 已經是一條長鏈（視差位移 → 自身旋轉 → hover 放大 → 鏡射），animation 一旦動到 `transform` 就會整條蓋掉。改在外層用**獨立的 `rotate` 屬性**：兩層各自轉、瀏覽器自然相乘，互不干擾。`transform-origin: 50% 8%` 放在頂端——拍立得是用迴紋針夾著的，從夾點擺盪才對。900ms 四拍遞減（−3.2° → +2.4° → −1.4° → +0.6°）跑一次就停，離開再進來會重播；持續晃很快就吵。

**手寫小字在「偷偷放閃」那張**，兩個理由：一是海邊那張的白邊被日期貼紙與這張拍立得壓住，字寫上去看不到；二是文案本身就在呼應這張的 alt「偷偷放閃」。兩張都給了晃動（同一種物件，只有一張會動看起來像壞掉）。

**幾何全部是量出來的，寫在 `useInviteScene` 的 `caption` 而不是元件裡**（跟座標同一個原則：微調只改資料檔）。卡片下緣做線性擬合得傾角 **+6.4°**（最大殘差 0.9px），文字塊跟著轉同樣角度才貼得住卡片。字級用 `cqw`（容器是 `.si-link`，`container-type: inline-size`），物件放大縮小時字會跟著縮。

**一行放不下**：文案 15 個字，白邊可用寬只有卡片的 59%（桌機 178px），一行等於每字 12px，糊成一團。拆成兩行。

**再加對話框**（使用者回報「好像會看不清楚」）：手寫細字壓在照片與白邊的交界上讀不清楚。墊一層 `--color-paper` 底、`--color-line` 細框、`--shadow` 淺影的圓角框，頂端一個旋轉 45° 的小尾巴指回照片裡的兩位主角。**內距／圓角／尾巴一律用 `em`**，跟著 `--cap-size` 一起縮放，換斷點或改字級都不會走樣。尾巴的作法是「只留左上兩邊框、內部填底色」——填色會蓋掉框體自己的上緣，接縫就消失了。

手機版沒有 hover，所以這整段是桌機限定的彩蛋。連結本身已有語意 `alt`，對話框掛 `aria-hidden` 純裝飾。

### 20. 引言對齊「Alex」的 A —— 對齊基準要回設計稿量，不要從算圖上臆測

使用者回報引言那三行沒對齊 logo。這題我猜錯兩次（先對齊 `Invitation` 的墨跡左緣、再對齊它花體 ℐ 的字身），兩次都被打回。

**正解是回設計稿量**：Figma 原稿裡引言左緣 253px、`Alex` 的 A 在 258px——**同一條垂直線**。而 `Invitation` 的花體 ℐ 在 315px，在稿子裡反而比引言更右，根本不是基準。也就是說 logo 是「三行階梯狀往右下排」，引言接的是**最上面那行的左緣**，不是最下面那行。

改成 `left: 29.5%`，引言左緣落在 196px，與 `Alex` 的 A（196px）完全重合。

**教訓**：這頁的每個座標都是從設計稿量出來的（§11／§12），對齊關係當然也在稿子裡。在算圖上比對「哪一條線看起來比較順」是在重新設計，不是在還原設計——量稿子只花兩分鐘，猜了兩輪都沒中。

順手修掉一個隱性 bug：`.invite-tagline` 的 `z-index` 是 40、蓋在海邊拍立得（z 24）上，區塊右半邊是空的但照樣攔截滑鼠，等於把那張拍立得的左半邊 hover 與點擊吃掉。補 `pointer-events: none`。

### 21. 手機版的手寫小字是常駐的，文案也不一樣

手機沒有 hover，桌機那顆藏起來等 hover 的對話框在手機上等於不存在。所以 `SceneCaption` 多一個 `mobileLines`：桌機 hover 浮現「借你墨鏡😎／我們要放閃了！」，手機常駐顯示「婚紗相簿」——後者不只是替代品，它在手機上還兼任「這張可以點」的提示。

兩顆各自渲染成獨立元素，由 `@media (min-width: 1024px)` 決定誰出現，不用 JS 判斷斷點（SSR 兩端輸出一致，無 hydration 風險）。手機的拍立得只有 209px 寬，同一個 `--cap-size` 換算出來的字太細，所以 `.si-caption-static` 把字級乘 1.5。

### 22. 三個貓掌印變成互動：Healthy／Money／Happy 的招呼卡

新人家裡三隻貓，三個掌印各對應一隻，點下去跳出招呼卡（照片＋角色定位＋祝福詞，文案由新人提供、逐字照放）。卡片沿用 `/gallery` 燈箱同一套 `UModal` 用法——靠內建的 `title` 讓 dialog 取得 accessible name，Esc 與焦點鎖交給元件，不自己實作。

**踩到三個坑，都值得記：**

**① `container-type: inline-size` 會把 `<button>` 算成 0 寬。** §19 為了讓手寫小字的字級跟著物件縮放，在 `.si-link` 上加了 `container-type`。`.si-link` 同時掛在 `<a>` 與 `<button>` 上——`<a>` 沒事，`<button>` 直接被算成 0×0。圖片靠 overflow 還看得到，所以肉眼完全看不出來，但**按鈕本身按不到了**：金唱片的音樂開關其實已經默默壞了兩個回合，直到貓掌印點不動才抓到。修法是把 `container-type` 拆到 `.si-cap-host`，只掛在真的有手寫小字的物件上。

> 判準：`container-type` 只加在確定是 `<div>`／`<a>` 的容器上；要加在 `<button>` 上先量 `getBoundingClientRect()`。

**② 掌印素材太小，點擊範圍要另外補。** 桌機 3.5~4.9% 寬、手機最小只有 21×25px，遠低於 WCAG 的 44px 目標尺寸。`.si-cat::before` 放一個看不見的 `max(100%, 44px)` 方塊把可點範圍撐開，視覺完全不變。

**③ 拍立得的透明角落會把掌印的點擊整個吃掉。** 三個掌印原本 `z: 8`，壓在所有東西下面。拍立得是**旋轉後的卡片**，它的 `<img>` 矩形包含一大片透明角落——透明像素照樣攔截 pointer events，所以六個掌印（兩個斷點各三個）的中心點全部被拍立得接走，變成「看得到、按不到」。用 `document.elementFromPoint()` 逐一驗證才確認。

修法是把 `z` 從 8 提到 30。代價是 Healthy 與 Happy 兩個掌印原本被拍立得完全蓋住、現在會畫在照片上（前後對照圖確認過只有這兩處變化，其餘像素完全相同）。判斷是可接受的：貓走過桌面本來就會踩到照片，掌印半透明、落在海景照的天空與緞帶上、不壓到人臉；更重要的是**看不到就不會有人去點**。要維持原樣就得改掌印座標，那會動到已經校正過的版面。

### 23. 貓咪不做成 modal：牠是走上桌面的一個物件

§22 那版是 `UModal`——點掌印跳一張蓋在畫面上的卡。新人要的是另一種：**不換背景、不蓋住整個畫面**，貓從畫面外走進來趴在桌上，旁邊散落一張紙條。所以 `InviteCatCard.vue`（modal）整個換成 `InviteCatVisit.vue`（桌上的一層）。

**構圖：三隻都落在同一個位置，不各自出現在自己的掌印旁。** 量過整張桌面的佔位後，唯一完全沒有物件的區域是桌機 `x 76~100 / y 50~100`（只有緞帶斜穿而過，`z: 13` 在底下）。而 Healthy 的掌印在桌機是 `x 42.5~51.1 / y 40.2~53.1`——正中央，就地出現會整隻蓋掉信封與蕾絲愛心卡那個主焦點。

三隻共用同一個**右下角錨點**（`right`／`bottom`，不是中心點）：兩隻趴姿、一隻坐姿，長寬比從 1.51 到 0.92 都有，用中心點定位會各自跑掉；錨在「身體壓在桌面上的那一角」才會像同一隻貓走到同一個位置趴下。體型差異靠 `SceneCat.w` 逐隻給值把**高度**對齊（桌機趴姿 40%、坐姿 24.4%——坐姿寬＝趴姿寬 × 0.6095，由兩張素材的長寬比 1.5087／0.9196 反推），不是統一寬度——統一寬度會讓坐著那隻高出一大截。

**朝向**：三隻都要臉朝左（看向畫面內側與紙條）。Healthy 素材本來就朝左；Money 與 Happy 朝右，用 `facesRight` 標記後以 `scale: -1 1` 鏡射。王冠在頭頂正中、毛色沒有方向性，鏡射看不出來。

**時序就是敘事**：腳印 0 / 140 / 280ms 逐步浮現（三張掌印素材輪流用＋第二步鏡射，不然三步是同一隻腳蓋三次）→ 420ms 貓從右下角滑進來 → 820ms 紙條飄下。整段約 1.3 秒。貓落定後會蓋住最後一兩個腳印——那是對的，牠正踩在自己的腳印上。

**尺寸全部用 `cqw`**：`.cat-visit` 掛 `container-type: inline-size` 且 `inset: 0`，於是 `1cqw` ＝ 舞台寬的 1%。舞台本身跟著視窗高度等比縮放，貓與紙條才不會在小視窗變成巨物。（`container-type` 只含 `layout / style / inline-size`，不含 `paint`，不會裁掉內容；掛在 `<div>` 上也沒有 §22 ① 那個 `<button>` 被算成 0 寬的問題。）

**三個因為「不是 modal」而必須自己補的東西：**

1. **出口**。modal 有遮罩和 Esc，這一層沒有。補了三個：紙條右上角的 ✕、點薄紗（見 §24）、Esc。另外 window 的 `pointerdown` 會判斷 `target.closest('.cat-visit, .si-cat')` 當保險——它在薄紗加進來之前是主要出口，現在薄紗擋在前面，留著是為了任何薄紗蓋不到的情況。
2. **朗讀**。不是 dialog 就不會自動朗讀新內容。`.cat-visit` 裡留一個**常駐**的 `aria-live="polite"`（跟著內容一起掛就太晚了），內容變動時播「◯◯ 走到桌上來了」。掌印按鈕另外掛 `aria-expanded`。
3. **貓身要擋住點擊**。`.cat-visit` 整層 `pointer-events: none`，但貓自己得設回 `auto`：手機版貓身正好壓在「看婚紗相簿」的拍立得上，不擋的話點貓會直接跳去相簿頁。牠在 `.cat-visit` 內，所以點下去也不會被判成「點畫面別處」而收起。

**已知取捨**：加了薄紗之後，換另一隻貓一律要兩下（先收起再點）——薄紗是遮罩，會把點在掌印上的那一下接走。這是遮罩的常規行為，換取的是「一次只有一隻貓、畫面乾淨」。（想直接換貓的話得把三個掌印的 `z` 提到薄紗之上，但那樣手機版的掌印會畫在紙條上面，更糟。）

**文案**：Happy 那張由新人提供、逐字照放；Healthy 與 Money 依同一結構（名字／角色兩行／悄悄話兩行／結尾一句）自 §22 的既有招呼詞改寫，**待新人確認**。

### 24. 貓出場時鋪一層薄紗，紙條同時放大一級

新人回饋兩件事：桌面太滿，貓與紙條看不出是主角；桌機的紙條字太小看不到。兩件是同一個問題的兩面——這張稿本來就是滿版的花、緞帶、照片與花體字，任何新東西丟上去都會被吃掉。

**薄紗**：`.cat-veil`、`rgb(250 247 241 / 62%)`，420ms 淡入。用紙色（`--color-paper` 就是背景底色）而不是純白——純白蓋在米色紙上會浮出一層灰膜。

**它掛在 `.invite-root` 而不是舞台內**（第一版掛錯位置，新人回報「白底透明的部分應該要滿寬」）。舞台寬度是 `min(100%, 100dvh × 1440/1024)`——由視窗高度反推的，所以視窗只要比它寬，兩側就會露出沒被壓淡的紙紋與葉影。`z-index: 44` 剛好卡在所有桌面物件（最高 42）之上、`.cat-visit`（45）之下。它不能用 `position: fixed` 留在原位逃出去：`.cat-visit` 有 `container-type: inline-size`，那隱含 `contain: layout`，會讓它變成 fixed 子孫的 containing block。

它同時是這一層的遮罩（點擊收起）。順帶解掉一個舊問題——沒有薄紗時，「點畫面別處收起」會連底下物件的點擊一起觸發（點在信封上會一邊收起一邊跳去 `/story`）。

**貓與紙條的最終尺寸**（放大兩輪後）：

| 紙條（手機） | 64cqw / 3.45cqw 字 | **96.9cqw / 5.56cqw**（250→378px 寬、13.5→21.7px 字） |

**桌機的紙條位移要看貓的頭頂在哪，不是看紙條自己。** 新人指定「往上 40px」，但同一輪貓也從 29% 放到 40%——貓的頂端因此往上跑了 10%（`y 65.5 → 55.7`），40px 完全不夠，紙條下緣仍壓在王冠上。王冠的位置是量出來的：素材上緣往下 10% 那一段，`cat-happy` 是 x 64.8~79.4%（鏡射後 20.6~35.2%），換算成舞台是 `x 68.2~74.1 / y 55.7~59.4`。`bottom` 要提到 44.5%（比指定的 40px 再高 73px）紙條下緣才落在 `y 56.7`，三隻的王冠才都完整露出。最終水平位置 `right: 23.2%`（合計往左 320px），紙條落在 `x 42.8~77.5`、貓在 `x 60~100`：兩者仍有水平重疊，但紙條下緣已在貓的頭頂之上，交疊處是空桌面。
