# Phase 5 決策權限分級表

> **上位規範**：[ops/judgment-rubrics.md](../../../ops/judgment-rubrics.md) 第 3 節「何時停下來問使用者」是唯一真理來源，本檔只把該節的判準**具體化到 Phase 5 的實際情境**，不重列該節既有的必停清單。本檔任何一級都**不得**與該節矛盾——凍結區、[maintenance.md](../../../ops/maintenance.md) 第 1 節「動前必問」清單、vibe spec 刪改，一律照該節規則停下來問，本檔不重複也不放寬。

## 一、自決不回報

以下情境自行決定即可，不需要在回報中特別說明理由。

| 情境 | 動作 |
|------|------|
| 表單形式（欄位排列、單欄或多欄、輸入元件挑選） | 依 `ui-config.yaml` 與既有頁面慣例決定 |
| 欄位標籤同義詞（spec 只鎖語意、沒鎖死文字） | 挑語意相符的中文標籤，不必逐字比對 spec |
| 分頁筆數 | 從 `ui-config.yaml > table.pagination.pageSizeOptions` 挑一個既有檔位，不自訂數字 |
| 前端防呆（必填提示、輸入長度限制、即時驗證訊息） | 依既有頁面慣例加上 |
| 圖示挑選（NuxtUI icon 內語意相符的圖示） | 自行挑選，不必列候選比較 |

## 二、自決但回報理由

以下情境可以自行決定並繼續做，但回報時必須寫明理由，讓使用者事後能追查。

| 情境 | 動作 |
|------|------|
| 偏離 skill 範本（發現範本本身有錯，或範本寫法與 route-map.yaml 衝突） | 以較具體的規範為準（route-map.yaml 是路由與 feature 對照的單一真相來源，優先於範本的預設寫法）；回報中寫「為何偏離＋改用哪份規範」 |
| 發現可抽共用邏輯的機會（如兩個頁面重複同一段驗證邏輯） | 先完成當前頁面的實作，把抽取的提案寫進回報；**不要**在頁面實作當下就新建共用檔——新增 `app/` 跨頁共用檔屬於第三級，必須先問 |

## 三、必停下來問

以下情境命中任一項就停手，不要先做再回報。

| 情境 | 動作 |
|------|------|
| 判斷下去需要放寬 server 授權（新增角色可存取範圍、放寬 ownership 過濾） | 停。先走第四節判準確認是否真的需要放寬，仍需要就列選項給使用者裁決 |
| 任務會動到凍結區（`test/e2e/specs/`、`spec/gherkin-feature/`、`spec/e2e-flows/`） | 停。依 [rules/frozen-paths.md](../../../rules/frozen-paths.md) 的三步驟處理，不寫 sentinel 繞過 |
| 懷疑 spec 本身寫錯（斷言與 `.flow.md` 或業務邏輯明顯矛盾） | 停。spec 是合約，永遠不為了通過測試而動它；把矛盾點列給使用者，走「改 flow 後重新產出 spec」或人工確認 |
| Phase 5 實作過程中發現需要新增 `app/` 下的跨頁共用檔（component、composable、store） | 停。列出用途與影響範圍，等使用者確認再建 |

> 例外：skill 範本已寫明位置與內容的共用檔（如 [pitfalls.md](pitfalls.md) 第 6 條的 `app/utils/display.ts`）直接建，回報時列出。
>
> 本 skill 在分身裡執行，「停」＝這一項不做、把選項與影響寫進回報、結束本次呼叫；使用者決定後再重新執行（見 SKILL.md「分身只做、不問」）。

## 四、判準：測試要的前置狀態被守門擋住時怎麼辦

**先問能不能用合法身分構造該狀態，再考慮改守門。** 守門檔住不代表守門設計錯了，多半是呼叫方式不對；改守門是最後手段，不是第一個念頭。

- **正例（查完發現不必動守門，屬於自決範圍）**：測試要驗「登入後才能操作自己的資源」的頁面，實測卡在 403。查證後發現是 spec 呼叫 API 時沒帶 auth header，不是授權設計錯誤——改用資源本人的身分呼叫即可解決，不動 server 授權一行程式碼。
- **反例（查完發現守門設計本身就是這樣要求，必須停下來問）**：測試要驗「A 角色能看到 B 角色建立的資源」，實測卡在 403。查證後發現 `route-map.yaml > rbac` 的 ownership 設定就是「只能看自己建立的」，這與凍結合約（rbac 區塊）本身牴觸。此時不可自行放寬 ownership 過濾，停下來問使用者，取得裁決後才做「最小範圍過濾」的放寬。

判斷順序：

1. 先查呼叫方式（有沒有帶正確的登入身分／token／header），這一步查不出問題再往下一步
2. 再查測試資料是否確實符合守門要求的身分關係（如 ownership 是否真的匹配）
3. 前兩步都排除後，才視為「守門設計與凍結合約牴觸」，停下來問——不要跳過 1、2 直接假設是守門的問題
