# Verify AC

把 issue 的 `## 驗收標準` 從「寫給人看的裝飾」變成**可執行的驗收關卡**：逐條驗、給證據、未過就修。職責是 **驗收 → 有限度修正 → 報告**，與 `/commit`、`/pr` 解耦。

**核心鐵律：逐條驗收一律附證據，判不出來就寫「無法判定」——絕不因為「看起來應該有做」就給 Pass。** 驗收的價值來自它會擋人，會放水的驗收等於沒有。

## 工作流位置（單一職責）

```
/new-issue   →  建 issue #N（四段 body，含 ## 驗收標準）
   ↓ 開發（/feature-to-api → /feature-to-ui → /test）
/verify-ac   →  逐條驗收 → 未過自動修（≤2 輪）→ 勾回 issue ＋ 留記錄（本 skill）
/commit      →  把改動變成 commit
/pr          →  push → PR 草案 → gh pr create
```

本 skill **不 commit、不 push、不開 PR**。修完停在工作區，收尾提醒使用者跑 `/commit`——這條界線跟 `/pr` 的「不越界代勞」同源，別破。

## 流程

### 1. 前置檢查（硬關卡，不通過就停）

| 檢查 | 命令 | 不通過 → |
|------|------|---------|
| gh CLI 可用且已認證 | `gh auth status` | 提示 `gh auth login` |
| 在 git repo 且有 GitHub remote | `gh repo view --json nameWithOwner` | **停**，這不是 GitHub repo |
| 解析得到 issue 編號 | 見下 | **停**（與 `/pr` 的差異見下方說明） |
| issue 有 `## 驗收標準` 段 | `gh issue view <N> --json body -q .body` | **停**，告知該 issue 沒有 AC，建議先補；不代擬、不硬驗 |

#### 解析 issue 編號

`$ARGUMENTS` 有給編號就直接用。沒給則**照 [../pr/SKILL.md](../pr/SKILL.md) 步驟 2「從分支名解析 issue 編號」執行**（本 repo 目前只有這一層：`feature/#145-issue-ac-loop` → `145`）。該節是唯一 SoT，**本檔不重複命令、不另寫一套**。

與 `/pr` 的差異只有一處：`/pr` 解析不到時是「略過 `Closes`，繼續發 PR」；**本 skill 解析不到就停**——沒有編號就沒有 AC，整件事無從進行。停下來時明說已試過什麼，不猜編號。

### 2. 取出驗收條目

```
gh issue view <N> --json body -q .body
```

- 取 `## 驗收標準` 段落下的 `- [ ]` / `- [x]` 條目，保留原文與順序
- 一併取 `## 範圍` 段的「範圍外」清單（步驟 4 的超編檢查要用）；沒有該段就跳過超編檢查，不報錯
- issue 已勾的 `- [x]` **仍要重驗**——勾選反映的是上次驗收當下的狀態，程式碼後來可能又動過

#### 確認實作在哪（漏掉會全盤誤判）

本 skill 預設在**當前工作區**驗，但 issue 的實作未必在這裡：分支還沒 merge、驗的是別人的 issue、或人在另一條 worktree（本專案慣例是一 issue 一 worktree，`.claude/worktrees/issue-<N>/`，這種情況很常見）。**實作不在當前分支時，每條 AC 都會因為「檔案不存在」被判成 Fail，然後觸發自動修去重建一份早就存在的東西。**

動手驗之前先確認：

- issue 的分支是否就是當前分支（步驟 1 解析已經查到）
- 不是 → 用 `git show '<branch>:<path>'` 跨分支讀（整個 rev:path 用單引號包住——分支名含 `#` 的 repo 慣例，見 `/new-issue` 注意段），**不要切分支**（工作區可能有未 commit 改動）
- 判不出實作在哪 → **停下來問使用者**，不要假設就是當前分支

**跨分支時整趟唯讀**：實作不在當前分支就**只驗不修**——步驟 4 自動修僅在實作位於當前工作區時進入；跨分支驗出的 Fail 直接列入報告交還使用者（在錯誤的工作樹上修，等於把別條分支的實作寫進不相關的地方）。

### 3. 逐條驗收（本 skill 的重點）

每條給三態之一，**一律附證據**：

| 判定 | 意義 | 證據要求 |
|------|------|---------|
| **Pass** | 確實達標 | `檔案:行號`、指令輸出、或實際執行結果。不接受「已實作」這種空話 |
| **Fail** | 明確沒達標 | 指出缺什麼、現況是什麼 |
| **無法判定** | 本環境驗不了 | 說明**缺什麼才能驗**（如需要外部 CLI、需要人眼判斷視覺、需要線上環境） |

驗法依條目性質選，能自動驗的就實跑，不要用讀 code 代替執行：

- 產出物存在性 → 讀檔／`ls`／`grep`
- 行為結果 → 跑對應測試或指令，貼輸出
- 規範／文件類 → 除了檢查檔案存在，**還要確認有消費點**：沒有任何 skill／`.claude/rules/`／`CLAUDE.md` 引用它 = 不算完成，判 Fail 並指出缺的是接線不是檔案
- 視覺／設計類 → 多半是「無法判定」，老實寫，交還使用者

**禁止**把「無法判定」寫成 Pass 來讓報告好看，也禁止寫成 Fail 去觸發不必要的自動修。

### 4. 未達標 → 自動修（上限 2 輪）

有 Fail 條目才進入本步驟；只修 **Fail**，**不碰「無法判定」**（那要人決定）。

每一輪：

1. 挑本輪要修的 Fail 條目，說明打算怎麼修
2. 改檔（授權邊界見下）
3. 跑驗證：`npm run eslint` + `npm run typelint`；動到 `app/`／`server/` 另跑 gate（`npx playwright test --config playwright.gate.config.ts`）
4. 重驗該條，更新判定

**授權邊界**（超出就停下來問，不自行擴權）：

| 項目 | 邊界 |
|------|------|
| 可動 | 與 Fail 條目直接相關的實作檔（`app/`、`server/`），以及該 issue `## 範圍` 的「範圍內」清單所列 |
| 不可動 | 凍結區 `test/e2e/specs/`、`spec/gherkin-feature/`、`spec/e2e-flows/`（見 `.claude/CLAUDE.md` Vibe UI 守則）；issue「範圍外」清單所列 |
| commit／push | **一律不做** |
| GitHub issue | 可勾 Pass 條目的 checkbox、可發驗收記錄 comment；**不改條目文字、不動其他三段、不關 issue** |
| 裝依賴／刪檔 | 不做，先提出 |

**超編檢查**：若為了修 Fail 必須動到 issue「範圍外」的東西 → **停**，告知使用者「這條 AC 需要超出 issue 範圍才能達成」，讓使用者決定是改 issue 範圍、拆新 issue、還是放棄該條。這是 `## 範圍` 必須分內外的用途。

**達 2 輪上限仍有 Fail** → 停，交還使用者，附**完整失敗軌跡**：每輪改了什麼、跑出什麼錯、目前還差哪幾條、你的假設是什麼。**禁止第 3 輪同法重試**——同一招沒用兩次就換人判斷，不要靠重跑碰運氣。

### 5. 收尾報告

固定格式：

```
issue #<N>：<標題>
驗收結果：<x> Pass / <y> Fail / <z> 無法判定   （自動修 <n> 輪）

- [x] <條目原文>
      ✅ Pass — <證據：檔案:行號 或 指令輸出>
- [ ] <條目原文>
      ❌ Fail — <缺什麼>
- [ ] <條目原文>
      ⚠️ 無法判定 — <缺什麼才能驗>
```

末尾依結果給下一步：

- **全 Pass** → 「改動停在工作區，接著跑 `/commit`」
- **仍有 Fail** → 列出待處理項，說明卡在哪，**不催促 commit**
- **有「無法判定」** → 明確請使用者**人工驗證後自行勾選**——本 skill 永遠不勾這類條目，重跑一百次也不會變，不接手就會一直讓 `/pr` 提醒下去

#### 寫回 issue（勾選 ＋ 留證據）

驗完**直接把結果同步回 GitHub**，讓「做完沒」有客觀依據，不必靠對話記憶：

1. **重建勾選狀態（雙向）**：重讀一次 issue body（`gh issue view <N> --json body -q .body`，避免覆蓋期間他人的編輯），依**本輪判定**重寫每條 checkbox：Pass → `- [x]`；Fail／無法判定 → `- [ ]`。**上輪勾了、這輪 Fail 的要取消勾**——迴歸不可以被舊勾選遮住，否則 `/pr` 讀到假的全勾就放行了。寫入暫存檔後 `gh issue edit <N> --body-file <暫存檔>`。
   **只動 checkbox 那一個字元**——不改條目文字、不動其他三段。
2. **留驗收記錄**：`gh issue comment <N> --body-file <報告暫存檔>`，內容即上方逐條結果表。這是勾選的證據來源——只勾不留記錄，等於回到「不知道憑什麼勾」的原點。

重讀時發現條目文字與步驟 2 取到的不一致（issue 被編輯過）→ **停**，不要硬寫，告知使用者並請重跑。

> 勾選由本 skill 代打是刻意的：勾選要有證據才有意義，而證據只有剛驗完的當下拿得到。使用者仍可自行改勾——下次驗收會重驗、以實際狀態為準。

## 注意

- 本 skill 只驗、修、回寫驗收狀態，**不 commit、不 push、不開 PR、不建 issue、不關 issue**——各自交給 `/commit`、`/pr`、`/new-issue`。
- issue 編號解析的 SSOT 在 [../pr/SKILL.md](../pr/SKILL.md) 步驟 2，改那裡要回頭確認本檔敘述仍成立。
- AC 條目的格式合約由 [../new-issue/SKILL.md](../new-issue/SKILL.md) 步驟 2 定義（`## 驗收標準` 段標題 + `- [ ]`）；那邊改格式，本檔的解析要跟著改。
- 條目寫得太模糊而無法客觀判定（如「功能正常」）→ 判「無法判定」並指出該條 AC 本身要重寫，不要勉強猜一個結果。
- `$ARGUMENTS` 給了編號 → 以它為準，跳過分支解析（方便驗非當前分支的 issue）。
