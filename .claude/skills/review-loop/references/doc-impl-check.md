# 文件與實作一致性檢查（專項 prompt）

`/code-review` 沒有參數可以指定檢查焦點。#173 的 eval 顯示，它漏抓的 Copilot 必修裡有一半是同一類：**文件寫的跟程式實際做的不一樣**。本檔是補這個洞的專項檢查，派一個 fresh subagent（`model: sonnet`）執行。

## 誰呼叫、何時跑

| 呼叫端 | 時機 | 目標 diff |
|---|---|---|
| `/ship` Phase 1 L5 | `/code-review` 之後 | `<merge-base>`（到工作區：路線 A 這時還沒 commit；未追蹤新檔先照 ship L5 段 `git add -N`） |
| `/review-loop` 第 2 節第 0 步（本地先審） | `/code-review` 之後、第一次 push 之前 | `<merge-base>`（前置檢查已要求工作區乾淨，等於全部已 commit 的改動） |
| `/review-loop` 每輪 7b | `/code-review` 之後、第 8 步 commit 之前 | 工作區 diff（本輪修正；本輪新增的檔先 `git add -N`，否則 `git diff` 看不到） |

**diff 不含任何 `.md` 檔 → 跳過**，不派分身。L5 的綠燈＝`/code-review` 與本檢查都沒有必修。

## 派工 prompt（照抄，填入 `<…>`）

```
你是審查員，只查一件事：文件描述與實作是否一致。其他問題（風格、效能、一般邏輯錯誤）不要報，那是別的審查員的事。

範圍：`git diff <目標 diff>` 裡改動到的檔案，加上它們引用或被它們引用的檔案。repo 在 <repo 根目錄>，你可以讀任何檔、跑唯讀指令。

對每個改動到的 `.md`，把它寫到的「可驗證主張」逐條找出來，再去實作端核對：
1. 指令與旗標：文件寫的指令、參數、旗標，實際腳本／工具有沒有、行為一不一樣
2. 路徑、檔名、行號、段落編號：指到的東西存不存在、指的是不是它說的內容
3. 正則、glob、pattern：文件說「會匹配 X」，實際 pattern 對 X 的結果（能實測就實測，貼出指令與輸出）
4. 數值與上限：逾時、次數、輪數、欄位數；文件說的數字和程式算出來的一不一樣（例如每次 5 秒乘 60 次不是 60 秒）
5. 流程順序與分支：文件說「先 A 再 B」「X 時跳過」，實作的順序與條件是不是這樣，有沒有永遠走不到的分支
6. 範例程式碼：文件裡的 snippet 能不能照抄就跑（缺 import、缺前置、用錯 API）
7. 多處描述同一件事：兩份文件，或文件與程式註解，對同一行為的說法互相矛盾

反方向也要查：改動到的腳本或程式，如果有文件在描述它（用 grep 找檔名或函式名），描述有沒有跟著改。

每一條都要讀到實作端的原文才下結論。能跑的就跑，不要用推理代替實測；沒實測的在 summary 標「未實測」。

輸出：只輸出一個 JSON 陣列，最多 10 筆，依嚴重度排序。每筆：
{"file": "<文件或程式的路徑>", "line": <行號>, "summary": "<一句話：文件說什麼、實作實際是什麼>", "failure_scenario": "<照文件做會發生什麼錯>"}
沒有發現就輸出 []。
```

## 結果怎麼用

- 回來的每筆照 `/code-review` 的 findings 同樣處理：落在本 PR diff 內的檔案、講得出具體改法的 → 當必修修掉；其餘歸「待使用者決定」。
- 起手的本地先審與 7b 只跑一次，不因為修了又重跑，避免自己審自己的修法無限循環。
